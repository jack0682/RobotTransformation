# 44 RX 상주 프레임워크 개념 명세

**문서 식별:** RX-CNS-1.0 · **원본 작성일:** 2026-09-23(사전 연구 RX-CNS-0.1) · **채택일:** 2026-09-29 · **상태:** [마스터 플랜](42_framework_master_plan.md) Phase 1에서 채택한 개념 명세. 채택은 규칙의 의미를 확정한 것이며 구현 완료의 근거가 아니다(14.3절).

## 0. 문서의 지위와 읽는 방법

이 문서는 제품 정의·가치 기준·기존 계약에서 확인한 철학과, 2026-09-21~23 설계 논의에서 확인한 상주 프레임워크·운영 중 변경·호스트 실행 관리 요구를 연결한 **개념 명세**다. 코어 판정 기준과 코드 분류는 [코어 헌장](43_core_charter.md)이 잇는다.

이 문서의 ‘해야 한다’와 ‘해서는 안 된다’는 채택할 운영 규칙의 초안이다. 현재 구현이 모두 충족한다는 뜻이 아니며, 기존 공통 계약 v1.0·셀 운영 계약·wire·SDK·manifest를 변경하지 않는다. 기존 계약의 범위를 확장하려면 별도 개정·호환성·이행 검토가 필요하다.

현재 제품 정의는 목적의 기준으로 사용한다. 설계 원칙 초안(`design_principles.md`, 미추적·미승인)은 철학을 해석하는 자료로만 사용한다. 그 문서의 특정 기술이 유일한 해법이라는 설명이나 과거 구현·검증 수치는 이번 명세의 필수 조건으로 승격하지 않는다.

코드·디렉터리·프로세스 개수·통신 수단·저장 기술은 정하지 않는다. Linux 수준의 실행 조건은 명세에 포함하지만 사용자가 제외한 `rx_ws/linux/` 소스 폴더는 조사 대상에 포함하지 않았다.

독립 검토 기록 두 건(v0.1, v0.2)은 사전 연구 저장소(`research_RX/research/rx_concept_spec_2026-09-23/`)에 있으며 이 저장소로 옮기지 않았다. 그 검토는 개념의 문서 대조이며 구현·현장 검증을 대신하지 않는다. v0.2 검토가 남긴 미결 RR01(여러 자원을 묶어 수락하는 책임), RR02(의존 결합과 갱신 책임), RR03(프레임워크 자체 변경 시 무엇이 계속되는가)은 14.2절 표에 이어 둔다.

## 1. 목적과 RX의 정의

### 1.1 목적

**서로 다른 로봇·설비·소프트웨어 기능을 연결해 하나의 일을 끝까지 수행하고, 참여자와 구현이 바뀌어도 작업의 책임·권한·결과·복구 상태를 일관되게 유지한다.**

이 목적은 제조뿐 아니라 운반·배송·점검·시설 서비스 등 여러 분야에 적용한다. 특정 제조사, 고정 셀, 특정 로봇 형태를 공통 개념의 전제로 삼지 않는다.

### 1.2 정의

**RX는 협업 시스템을 개발하고 지속적으로 운영하기 위한 Linux 기반 시스템 프레임워크다. 공통 실행 계약과 상주 런타임을 통해 구성요소의 참여·실행, 작업·자원·권한·상태의 수명과 변경을 관리한다.**

RX 프레임워크는 개발자가 사용하는 계약·개발 지원·운영 기능을 포함한다. RX 런타임은 실제 설치 환경에서 그 계약을 적용하는 실행 기반이다. 현장의 RX 시스템은 런타임, 등록된 구성요소, 실제 연결 대상, 설정과 운영 정책이 결합된 구체적인 운영 실체다.

### 1.3 개발자에게 제공할 약속

작성자는 자기 기능·사용 조건·실행 요구·결과 의미·상실과 변경 시 의무를 제공한다. RX는 등록·수명·자원 사용·권한·상태 추적·변경·복구의 공통 규칙을 제공한다.

이를 통해 후속 개발자가 다른 구성요소와 협업하기 위해 공통 운영 의미를 매번 새로 정의하는 부담을 줄인다. 장비별 실제 동작, 업무 목표, 현장 적합성에 관한 전문 지식은 해당 작성자와 현장 책임이 제공한다.

### 1.4 제품 가치의 조건

RX의 가치는 정확한 상태 표현과 실제 업무 진행을 함께 평가한다. 결과 불명을 보존한다는 이유만으로 유용한 시스템이라고 판단하지 않으며, 업무가 완료됐다는 이유만으로 근거 없는 주장과 권한 우회를 허용하지 않는다.

작업 완료, 비정상 개입, 미결의 수와 지속 시간, 복구 가능성, 새 기능 연결 부담과 운영 복잡성을 함께 관찰한다. 거절·중단·미결을 집계에서 빼거나 미측정을 0으로 표시해서는 안 된다.

## 2. 철학에서 명세로 이어지는 원칙

원칙은 기술 이름보다 먼저 존재한다. 다음 PH01–PH07은 이번 초안에서 사용하는 해석이다. 출처와 해석 범위는 15절에 연결한다.

| ID | 원칙 | 명세에서 요구하는 것 |
|---|---|---|
| PH01 | 전체 일을 끝내는 협업 | 부분 기능의 성공과 사용자가 요구한 최종 완료를 구분하고 연결한다 |
| PH02 | 주장에는 근거와 범위가 따른다 | 무엇을 관측했고 어떤 조건으로 무엇을 판단했는지 함께 남긴다 |
| PH03 | 공식 상태와 권한의 갱신 책임은 일관되어야 한다 | 충돌하는 범위에서 서로 다른 주체가 독립적으로 같은 권한·결과를 확정하지 않는다 |
| PH04 | 지원은 조건과 근거를 포함한다 | 기능 이름·설치·연결과 실제 사용 가능성을 구분한다 |
| PH05 | 실행보다 책임이 오래갈 수 있다 | 실행 상실·재시작·교체 후에도 원 작업과 남은 의무를 추적한다 |
| PH06 | 불명 처리는 운영 복귀와 연결된다 | 모르는 사실을 보존하면서 확인·복구·인계·종결의 경로를 제공한다 |
| PH07 | 규칙을 지키는 수단은 교체할 수 있다 | 공통 의미를 보존하며 언어·통신·저장·배치의 대안을 평가한다 |

### 2.1 ‘근거를 제시할 수 있다’의 의미

RX가 표현하는 관측은 특정 주체가 특정 조건에서 얻거나 보고한 정보다. 관측이 존재한다는 사실만으로 물리 세계의 모든 사실이 참이라고 증명되는 것은 아니다.

RX는 자신의 판단에 사용한 출처·관련 대상·작업·시각 조건·해석 규칙·검증 범위를 제시할 수 있어야 한다. 알고 있지 않은 출처·시각·완료 상태를 채워 넣어 판단 근거를 만들어서는 안 된다.

타입·검증·접근 경계·기록은 잘못된 주장을 어렵게 만들고 추적할 수 있게 하는 집행 수단이다. 그것만으로 장비 관측의 진실성이나 모든 현장 조건을 보증한다고 선언하지 않는다.

### 2.2 ‘권위가 일관된다’의 의미

원본 관측을 만드는 주체, 명령 전달 사실을 기록하는 주체, 작업 결과를 확정하는 주체는 다를 수 있다. 여러 관측자가 같은 대상에 대해 서로 다른 정보를 제공할 수도 있다.

명확히 해야 하는 것은 **어느 범위의 어떤 공식 상태·권한을 누가 어떤 규칙으로 갱신하는가**다. 서로 충돌하는 권한이나 결과를 각자 확정하는 경로를 허용하지 않는다. 원본 관측의 출처를 보존하고 상충하는 근거는 따로 기록한다.

이는 전 세계에 writer 프로세스 하나만 두어야 한다는 규칙이 아니다. 현재 v1의 단일 Runtime·writer는 해당 범위의 구현 선택이다. 다른 배치에서도 같은 논리적 권위의 의미를 지킬 방법과 범위를 명세해야 한다.

## 3. 책임과 적용 범위

### 3.1 RX의 공통 책임

- 구성요소·기능·지원 조건·의존 관계의 등록과 변경 관리.
- 실행 인스턴스, 준비 상태, 허용 범위와 남은 의무의 관리.
- 작업·개별 수행·결과·인계·미결의 식별과 연결.
- 협업 자원과 호스트 실행 자원의 사용 조건 조율.
- 현재 권한과 그 적용 범위의 판단·전달·집행 연결.
- 운영 중 추가·교체·제거의 영향과 전환 조건 관리.
- 접속·실행·호스트 상실 후 상태 대조와 복귀 판단 지원.
- 운영 판단의 이유·근거·한계를 조회할 수 있는 정보 제공.

### 3.2 작성자·현장·외부 시스템의 책임

| 주체 | 제공해야 할 것 |
|---|---|
| 기능 작성자 | 제공 동작, 입력과 결과 의미, 사용 조건, 실행 요구, 지원·미지원·불명 범위 |
| 협업·응용 작성자 | 업무 목표, 기능 조합, 성공 조건, 허용된 대기·분기·개입 정책 |
| 장비 연동 작성자 | 실제 명령·관측·중단·조회·인계의 의미와 제공 가능 범위 |
| 현장 통합 책임 | 실제 연결·도구·보정·공간·운영 조건과 그 확인 근거 |
| 호스트 실행 책임 | 승인된 OS 자원·격리·장치 조건의 실제 적용과 관측 |
| 운영자 | 권한 범위 안의 요청·판단·현장 확인·복구 조치와 그 출처 |
| 장비 제어·현장 보호 책임 | 로컬에서 집행해야 하는 제어·보호 동작과 지원 조건 |

하나의 사람이 여러 역할을 맡을 수 있다. 그러나 결정·증거·집행의 책임을 같은 것으로 합치지 않는다.

### 3.3 지원 범위의 선언

지원 선언에는 제공 기능, 의미와 제한, 실행·장비·환경의 조합, 확인한 근거와 미확인 부분을 포함해야 한다. 실제 업무 투입은 그 선언과 현재 현장 조건을 대조해 판단한다.

공통 개념으로 표현할 수 있다는 것, 구현이 존재한다는 것, 특정 설치에서 사용할 수 있다는 것을 구분한다. 다중 영역·물리 중간 인계·강하게 결합된 공동 제어는 각각의 추가 조건을 명세해야 한다.

## 4. 공통 개념

아래 용어는 개념 명세용이다. 최종 클래스·RPC·DB·파일 형식을 선택한 것은 아니다.

| 개념 | 정의 | 다른 개념과의 구분 |
|---|---|---|
| 운영 영역 | 특정 작업·상태·권한의 결정 책임과 정책이 적용되는 범위 | 컴퓨터 한 대 또는 물리 공간 하나와 동일하지 않음 |
| 계산 호스트 | 구성요소가 실제로 실행되고 로컬 OS 자원과 시계를 사용하는 환경 | 로봇이나 장비 수행 경계와 일대일이 아님 |
| 패키지 | 제공할 구현·계약·관련 자료를 배포·유지보수하는 묶음 | 설치·검증만으로 실행·업무 권한을 얻지 않음 |
| 구성요소 | 공통 계약에 따라 등록되고 관리되는 기능 제공 단위 | 프로세스·장비·Cell과 반드시 일대일이 아님 |
| 제공 기능 | 구성요소가 외부에 제공하는 동작·계산·관측과 그 조건 | 같은 이름만으로 서로 대체 가능하지 않음 |
| 등록 대상 | 특정 운영 맥락에서 식별·관리되는 구성요소와 연결 | 실제 실행이 없어도 등록과 지원 정보가 남을 수 있음 |
| 실행 인스턴스 | 어느 시점에 실제로 수행되는 구현의 실행 실체 | 재시작·새 실행과 지속적인 등록 신원을 구분 |
| 협업 역할 | 공동 목표에서 맡는 수행·판단 책임 | 같은 역할을 다른 주체가 조건에 따라 맡을 수 있음 |
| 작업 | 사용자나 상위 업무가 요구한 목표와 진행·종결 책임 | 개별 기능 반환값만으로 전체 완료를 판단하지 않음 |
| 개별 수행 | 특정 작업·목적을 위해 기능에 맡긴 실행과 그 결과 책임 | 전송 시도나 재조회와 동일하지 않음 |
| 자원 | 사용량·충돌·점유·접근·인계를 조율할 대상 | 계산 자원과 물리 자원의 회수 의미가 다름 |
| 관측 | 특정 출처와 조건에서 얻거나 보고된 정보 | 현재 진실·업무 결론과 자동으로 동일시하지 않음 |
| 근거 | 특정 판단을 지지하는 관측·기록·확인과 적용 범위 | 서명·보관 여부만으로 내용의 물리적 진실성을 보증하지 않음 |
| 판단 | 규칙과 근거를 적용해 허용·거절·진행·결과 등을 정한 기록 | 판단에 사용한 원본 근거와 구별 |
| 실행 권한 | 특정 주체가 특정 대상·범위·조건에서 행동할 수 있는 허용 | 로그인·프로세스 생존·등록 상태와 구별 |
| 협업 구성 | 역할·기능·현장 연결·의존 관계·운영 정책의 조합 | 변경 요청과 현재 실제 적용 상태는 다를 수 있음 |
| 변경 | 구성·담당·구현·조건을 바꾸려는 요청과 그 처리 책임 | 파일 교체 또는 관리 API의 응답만으로 완료되지 않음 |

기존 `Cell`은 현재 계약 범위의 협업 구성과 운영 조건을 표현하는 모델로 본다. 새 관측·계획·계산 구성요소의 존재를 모두 Cell 생성에 종속시키는 것은 이 초안의 기본 가정이 아니다. 기존 Cell 규범과 새로운 구성요소 모델의 연결은 별도 이행 대상이다.

## 5. 신원·수명·상태

### 5.1 유지할 신원과 새로 생기는 실행

등록 대상, 패키지 버전, 현장 구성, 작업·개별 수행, 실제 실행 인스턴스, 시계·부팅의 범위를 구분해야 한다. 같은 이름·주소·포트를 재사용했다는 이유만으로 같은 실행이나 권한이라고 판단해서는 안 된다.

같은 처리 책임의 재조회·재전달은 원래 요청과 연결한다. 같은 요청을 다시 받았다는 사실은 실제 장비 명령을 다시 호출할 권한이 아니다. 내용이 같아도 별도로 요청한 새 업무는 다른 수행일 수 있다. 동일 요청인지 여부를 내용 해시만으로 결정하지 않는다.

### 5.2 상주성

RX는 관리 도구의 접속과 구성요소 실행의 수명이 시스템의 등록·구성·작업·변경 책임을 임의로 삭제하지 않도록 해야 한다.

정상 종료·비정상 상실·재시작·전원 복구 뒤 무엇을 보존하고 다시 확인할지 명시한다. 필요한 기록을 잃었으면 이를 ‘과거 요청이 없었다’는 상태로 바꾸지 않는다. 복구할 수 있는 근거와 그 한계를 표시한다.

상주성은 모든 구성요소를 항상 실행한다는 뜻이 아니다. 필요에 따라 실행을 준비·중단·교체하더라도 공통 운영 체계와 남은 책임이 유지되는 성질이다.

### 5.3 독립적으로 표현할 상태의 의미

| 상태 축 | 알아야 할 내용 |
|---|---|
| 설치·등록 | 무엇이 알려져 있고 어떤 내용을 수용했는가 |
| 실행 | 어떤 실행이 실제로 생성·생존·종료했으며 무엇이 불명인가 |
| 준비 | 필요한 기능·의존 조건을 현재 만족하는가 |
| 업무 사용 허용 | 어떤 역할·작업·권한·현장 조건에서 사용할 수 있는가 |
| 수행 지식 | 요청이 전달·수락·진행·종료됐다고 어디까지 알고 있는가 |
| 업무 결과 | 정의된 성공·실패·취소·미해결 등의 결론을 내릴 근거가 있는가 |
| 근거의 일관성 | 기존 결론과 충돌하는 근거가 있는가 |
| 자원 의무 | 사용·점유·격리·인계 중 어떤 책임이 남는가 |

이 축들을 모두 하나의 ‘정상/오류’ 표시로 덮어쓰지 않는다. 동시에 실제로 같은 의미인 상태를 근거 없이 중복 생성하지 않는다. 위 표는 필요한 구분이며 최종 상태 열거형은 아니다.

## 6. 판정·기록·집행의 책임

중요한 전이에는 필요한 사실, 제공 주체, 최종 판단 책임, 실제 집행 책임, 남길 기록이 연결되어야 한다.

| 대상 | 공식 판단·갱신 책임 | 제공·집행 책임 |
|---|---|---|
| 구성요소 등록과 지원 정보 | 구성요소 관리 | 작성자가 내용·범위·근거를 제공하고 정책이 수용 범위를 판단 |
| 프로세스 생성·종료·실행 소유 | 호스트 실행 관리 | OS의 실제 상태와 실행 식별 근거를 관측; 수명 전이에 외부 효과가 있으면 해당 효과의 권한·조건을 함께 확인 |
| OS 정책 적용 상태 | 호스트 실행 관리 | 지원되는 OS 수단을 통해 적용하고 실제 상태 확인 |
| 작업·담당·결과·미결 | 해당 운영 영역의 작업 판단 책임 | 응용은 목표·정책, 실행 주체는 수행 근거 제공 |
| 협업 자원·행동 권한 | 해당 권한 범위의 자원·권한 판단 책임 | 장비 수행 경계가 현재 명령 조건을 집행하고 실제 점유 보고 |
| 원본 관측·native 전달 사실 | 해당 생성·전달 주체 | 출처와 관련성을 유지해 제공; 상위 작업 결과를 독자적으로 덮어쓰지 않음 |
| 재시도·업무 재개 | 권한이 확인된 작업 판단 책임 | 복구가 근거를 대조하고 호스트·장비가 허용 범위에서 집행 |
| 변경 적용·절차 재개 | 변경 조율 책임 | 관련 구성요소·호스트·장비가 단계별 적용 근거 제공 |
| 최소 관리 기반 기동·복구 | 설치된 신뢰 정책을 집행하는 OS·로컬 부트스트랩 | 관리 기반을 먼저 기동하고 업무 권한은 별도로 대조 |

표의 책임은 독립된 서비스 이름을 확정한 것이 아니다. 어느 배치에서도 같은 범위의 결정을 서로 충돌하게 내리거나 책임 없는 전이를 만들지 않아야 한다.

호스트의 실행 관리 권한은 장비의 물리 동작을 허용하는 권한을 대신하지 않는다. 시작·준비·종료가 모드·토크·물품 지지에 영향을 주면, 해당 효과의 판단 책임이 허용 조건을 확인하고 호스트 실행 관리는 그 조건 안에서 전이를 집행한다.

## 7. 공통 운영 규칙

다음 CN01–CN22는 이번 초안의 규범 후보다. 필수 조건을 만족하지 못하면 해당 전이를 보류·거절하거나 정의된 불명·복구 경로로 처리한다. 관련 없는 모든 기능까지 일괄 중단하는 규칙으로 확대하지 않는다.

| ID | 규칙 | 요구되는 의미 |
|---|---|---|
| CN01 | 근거와 판단을 분리한다 | 판단은 사용한 근거·규칙·적용 범위와 연결되어야 하며 원본 관측을 결론 값으로 덮어쓰지 않는다 |
| CN02 | 모르는 것을 실패나 미실행으로 바꾸지 않는다 | timeout·단절·응답 부재·현재 idle만으로 과거 수행 결과나 물리 중단을 확정해서는 안 된다 |
| CN03 | 공식 갱신 권위와 충돌 범위를 명시한다 | 동일한 상태·행동 권한의 충돌 범위에 독립적인 최종 판단 경로가 경쟁해서는 안 된다 |
| CN04 | 요청과 수행의 동일성을 보존한다 | 같은 요청의 재조회·재전달은 원래 책임·기록에 연결하며 새 물리 호출을 허가하지 않는다. 다른 의도의 키 재사용은 명시적으로 거절한다 |
| CN05 | 지원 조건과 근거의 한계를 보존한다 | 등록·설치·서명·프로세스 생존을 해당 업무의 지원 확인으로 승격하지 않는다 |

| CN11 | 결과 종결과 자원 인계를 분리한다 | 업무 결과·실행 종료·권한 만료만으로 잔여 명령·물품·공간의 의무가 해소됐다고 판단하지 않는다 |
| CN12 | 취소 요청과 취소 완료를 구분한다 | 중단·취소의 접수는 실제 효과의 종료 근거가 아니다. 성공·취소의 경합은 근거와 계약으로 판단하며, 정상 종료의 대기시간 만료를 강제 종료 허가로 바꾸지 않는다 |
| CN13 | 재시작으로 현재 권한을 자동 복원하지 않는다 | 남은 기록과 현재 실행·장비·시계 조건을 대조하고 확인된 범위에서 재개한다 |
| CN14 | 늦거나 중복된 요청의 적용 범위를 확인한다 | 이전 실행·권한·구성의 요청을 현재 요청처럼 실행하지 않는다. 필요한 직렬화·권한 세대 의미를 유지한다 |
| CN15 | 변경이 현재 작업의 의미를 조용히 바꾸지 않는다 | 기존 작업과 새 작업에 적용한 구성·기능·결과 의미를 구분하고, 현재 조건의 무효화는 별도로 반영한다 |
| CN16 | 변경 영향과 지속 운전 범위를 함께 판단한다 | 기능 의존뿐 아니라 진행 작업·공유 자원·결과 소비·호스트 조건을 확인하고 적용 가능한 범위를 정한다 |
| CN17 | 관리 기반의 기동 권한을 업무 권한과 구분한다 | OS·로컬 부트스트랩은 신뢰 정책으로 최소 관리 기반을 복구하되 장비 작업 권한을 자동 생성하지 않는다 |
| CN18 | 필요한 로컬 보호 책임을 공통 저장·연결의 성공에 종속시키지 않는다 | 단절·저장 실패 시 필요한 현장 반응을 별도 책임으로 두고, 반응 요청과 실제 결과를 구별한다 |
| CN19 | 판단 이유와 다음 책임을 설명한다 | 실행·대기·거절·불명·복구에는 적용 규칙, 부족한 근거, 담당과 허용된 후속 경로가 있어야 한다 |
| CN20 | 불명을 보존하면서 운영 복귀·종결의 경로를 제공한다 | 확인·복구·개입·재개·해결 불가 처분을 구분하고, 불명 결과를 숨기지 않은 채 남은 책임을 관리한다 |
| CN21 | 공통 의무와 선택 능력을 구분한다 | 모든 작성자는 의미·조건·미지원·불명을 설명해야 한다. 실제 조회·중단·중간 인계 능력의 부재는 지원 범위 제한으로 반영한다 |
| CN22 | 계약 변경의 의미와 이행을 추적한다 | 형식뿐 아니라 결과·권한·복구·지원 조건이 달라지면 영향을 검토하고, 기록된 과거 수행의 의미를 소급 변경하지 않는다 |

### 7.1 구현으로 강제할 것과 외부 근거로 확인할 것

예를 들어 임의 UI 입력이 완료 원장을 직접 쓰지 못하도록 하는 것은 API·권한·상태 전이·저장 경계에서 강제할 수 있다. 반면 센서가 실제 물체를 올바르게 관측하는지는 장비와 적용 환경의 근거가 필요하다.

각 규칙에는 무엇을 타입·검증·접근 제어·기록·집행 경계로 강제할지, 무엇이 외부 사실에 의존하는지, 위반·불명 상태를 어떻게 발견할지를 연결해야 한다. 경고 문구만으로 강제 의무를 충족했다고 처리하지 않는다.

### 7.2 근거의 강도를 구분한다

모든 기능에 동일한 센서·승인·물리 인계 의무를 강제하지 않는다. 기능이 만드는 효과, 업무가 요구하는 결론, 공유 자원에 미치는 영향에 따라 필요한 근거를 명시한다.

근거를 줄일 때에도 어떤 주장과 허용 범위를 줄였는지 설명해야 한다. 검증하지 않은 강한 주장을 유지하면서 확인 절차만 생략해서는 안 된다.

## 8. 구성요소의 공통 계약

### 8.1 작성자가 제공할 의미

| 항목 | 필수 설명 |
|---|---|
| 정체성과 제공 기능 | 무엇을 제공하고 어떤 구현·지원 버전을 사용하는가 |
| 입력·출력 | 요청과 결과가 무엇을 뜻하며 어떤 대상·작업과 연결되는가 |
| 사용 조건 | 어떤 조건이 준비·업무 사용에 필요하며 누가 확인하는가 |
| 의존 관계 | 필요한 기능·자원·장치·관측·외부 시스템은 무엇인가 |
| 실행 요구 | 어떤 호스트·시간·계산·장치 조건이 필요한가 |
| 상태·결과 근거 | 무엇을 관측할 수 있고 무엇은 알 수 없는가 |
| 수명·실패·중단·반복 | 생성·연결·준비·활성화·종료와 실패 시 어떤 효과가 생기거나 남으며, 조회·중단·반복은 어디까지 가능한가 |
| 변경·인계 | 어떤 시점과 조건에서 교체·제거·인계할 수 있는가 |
| 호환성 | 변경이 소비자·설정·작업·복구에 어떤 영향을 주는가 |
| 확인 범위 | 선언 중 실제로 확인한 것과 미확인인 것은 무엇인가 |

작성자의 ‘비구동’ 또는 ‘지원함’이라는 선언만으로 권한이나 검증 상태를 확정하지 않는다. 공통 정책은 출처·허용된 기능·실제 접근 경계·필요한 근거를 확인해 참여 범위를 정한다.

### 8.2 항상 필요한 의무와 선택적인 능력

항상 필요한 것은 제공하는 정보의 의미와 한계를 설명하는 의무다. 장비가 제공하지 않는 사실을 만들어 보고하라는 뜻이 아니다.

| 기능별 선택 능력 | 없는 경우 명세할 제한 |
|---|---|
| 이전 수행 조회 | 결과 불명 후 자동 대조에 필요한 외부 근거·현장 확인 또는 미지원 범위 |
| 진행 중 중단 | 신규 배정 중지와 현재 수행 처리를 구분하고 즉시 취소를 약속하지 않음 |
| 중간 물리 인계 | 현재 작업 완료 후 전환 등 실제 가능한 교체 방식만 제공 |
| 직접 완료·점유 관측 | 업무가 요구하는 결론을 위해 필요한 보완 관측이나 명시적 확인 절차 |
| 원격 시간의 유효성 확인 | 원격 정보에 근거한 현재 상태·권한 판단의 제한 |
| 특정 OS 자원 정책 적용 | 해당 실행 요구를 지원하지 않음을 표시하거나 허용된 대안을 새로 검토 |

### 8.3 참여와 사용 과정

내용과 계약을 검토해 등록한다. 실행 요구와 호스트 지원 조건을 대조한다. 승인된 환경을 준비하고 실행 소유권·실제 적용 상태·기능 준비를 확인한다. 업무 사용은 작업·역할·협업 자원·현장 조건을 추가로 확인한 범위에서 허용한다.

등록만 된 대상은 업무를 수행하지 않을 수 있다. 준비된 실행도 특정 역할을 맡지 못할 수 있다. 현재 사용할 수 없는 기능도 그 이유와 필요한 조건을 조회할 수 있어야 한다.

드라이버 시작·연결·초기화가 실제 장비 모드나 토크를 바꾼다면 그 준비 과정도 외부 효과가 있는 행동이다. 별도 업무 명령을 아직 보내지 않았다는 이유로 권한·기록·현장 조건 확인을 생략해서는 안 된다. 최소 관리 기반의 기동 권한도 이러한 효과를 자동 허가하지 않는다.

### 8.4 제거와 지원 종료

새 배정을 제한할 범위, 진행 중 수행, 결과 소비자, 자원·물리 의무를 확인해야 한다. 설치 파일이나 실행을 제거해도 남은 작업과 근거의 관계를 잃어서는 안 된다.

계획된 비활성화·정상 종료·정리 함수가 토크를 해제하거나 물품 지지를 없앨 수 있으면, 잔여 명령·현재 지지·인계 조건을 확인한 뒤 해당 전이를 허용한다. 정상 종료 대기시간이 지났다는 이유만으로 강제 종료를 허가하지 않는다. 프로세스를 유지하는 것만으로 물리 지지가 보장된다고 주장하지도 않는다.

지원 종료는 새 사용의 제한과 이전 기록의 해석 가능성을 구분한다. 어떤 버전·설정·작업에 영향을 주고 무엇을 이전해야 하는지 설명해야 한다.

## 9. 호스트 실행 계약과 OS 수준의 책임

### 9.1 실행 요구

구성요소는 자신의 기능을 제공하는 데 필요한 호스트 조건을 선언해야 한다. 시간 제약, 계산 자원, 메모리, 장치 접근, 통신·저장 조건 가운데 해당하는 요구를 포함한다. 요구하지 않는 조건과 아직 모르는 조건을 구분한다.

시간 요구에는 주기·응답 기한·관측 유효성·권한 만료·중단 후 확인 시간처럼 목적이 다른 제한을 혼합하지 않는다. 구체적인 수치가 필요한 보장은 단위·측정 경계·환경·부하·실패 조건과 함께 선언해야 한다.

### 9.2 수락·적용·확인

호스트 실행 책임은 선언을 그대로 성공 처리하지 않고, 지원하는 메커니즘과 현재 조건을 대조해야 한다. 적용 요청, 실제 적용 상태, 기능이 요구를 충족한 근거는 구분해야 한다.

예를 들어 자원 제한이 설정되었다는 사실은 최악 응답 시간을 입증한 것이 아니다. 프로세스를 격리했다는 사실도 공유 메모리·장치·호스트 장애의 모든 영향을 제거했다는 뜻은 아니다.

적용할 수 없는 필수 조건은 명시적으로 거절·보류한다. 낮은 조건으로 바꾸려면 변경된 요구와 허용 범위를 별도 판단해야 하며, 무통보 강등을 허용하지 않는다.

### 9.3 위반과 실행 상실

자원 한계 초과, 적용 상태의 이탈, 실행 지연, 프로세스 상실을 관측한 범위대로 보고한다. 이 사건으로 어떤 업무·관측·변경 조건이 영향을 받는지 운영 판단에 연결한다.

계획된 시작·종료는 8.3–8.4절의 외부 효과 조건을 따라야 한다. OOM에 의한 종료·비정상 상실·전원 손실처럼 의도한 절차를 거치지 못하는 경우에는 실제로 잃은 실행과 미확인 효과를 기록·대조하고, 사전에 정한 로컬 대응에 연결한다. OS 정책은 이러한 상실의 물리적 결과를 고려해 선택·검증해야 하며 RX 소프트웨어가 모든 실행 상실을 막는다고 가정하지 않는다.

호스트 자원을 회수했다고 협업 자원이 인계됐다고 처리하지 않는다.

### 9.4 기술 선택의 위치

CPU 스케줄러, 자원 제어, 시간·장치·저장·격리 메커니즘은 이 계약의 집행 수단이다. 지원 커널·보드·드라이버와 필요한 확장 여부는 조건을 근거로 선택한다. 이 문서는 특정 커널 옵션이나 배포 구성을 채택한 것이 아니다.

## 10. 작업·결과·자원 인계

### 10.1 업무의 시작과 수락

요청의 목적·범위·관련 작업을 식별하고, 수락한 처리 책임을 보존해야 한다. 같은 요청의 응답을 잃으면 원래 요청을 조회·대조해야 한다. 중복 전달에는 원래 처리 기록·현재 상태를 반환하고, 중복 전달 자체를 실제 장비 명령의 재호출 근거로 사용하지 않는다.

일반 물리 명령이 전달됐을 가능성이 생긴 뒤에는 같은 키·같은 수행을 유지하더라도 실제 명령을 자동 재호출하지 않는다. 새 키 발급이나 어댑터·SDK의 내부 재시도로 이 경계를 우회해서도 안 된다. 아직 명령을 호출하지 않았다는 근거가 있는 준비 상태에서는 현재 권한과 조건을 다시 확인해 원 수행을 진행할 수 있다. 호출 전후를 구분할 수 없으면 이 예외를 적용하지 않는다.

조회, 별도 목적의 복구·취소, 로컬 보호 반응은 원래 생산 동작의 재호출과 구분한다. 각각의 신원·권한·기록·반복 조건을 따라야 하며, 이름만 복구로 바꿔 원 동작을 반복해서는 안 된다. 부작용이 없는 계산·조회에는 해당 기능의 재시도 계약을 적용할 수 있다.

요청 수락, 기능 수행 준비, 실제 전달 가능성, 장비의 접수, 업무 결과의 기록은 서로 다른 의미다. 해당 기능에서 적용되지 않는 단계는 그 이유를 명시할 수 있다. 상태가 이미 만족되어 실제 쓰기가 필요 없는 경우도 수행 의미에 포함한다.

### 10.2 결과의 판단

성공·실패·취소 등 결과는 해당 수행에 연결된 근거와 업무가 정한 조건으로 판단해야 한다. ‘이동 완료’, ‘물체 전달’, ‘다음 참여자의 인수’, ‘사용자의 수령’은 필요한 경우 별도 사건과 조건으로 구분한다.

서로 충돌하는 근거가 들어오면 기존 결과를 조용히 덮어쓰지 않는다. 원래 판단과 새 근거의 관계, 영향을 받는 현재 사용 범위, 조사·정정의 책임을 별도로 기록한다. 상충이 해소되지 않은 결과를 정상 성공으로 표시하거나 다음 행동의 전제조건으로 사용하지 않는다. 이미 그 결과에 의존한 작업·자원도 영향을 대조하고 필요한 범위의 후속 사용을 제한한다. 관련 없는 작업까지 일괄 정지시키지는 않는다.

장비 재시작으로 현재 조건이 무효가 된 것과 과거 완료의 근거가 서로 충돌하는 것은 구분한다. 정정이 필요하면 원 판단을 참조하는 별도 조사·처분 기록으로 남겨 원래 판단과 변경 이유를 함께 해석할 수 있게 한다.

### 10.3 불명의 처리와 업무 종결

결과를 확인할 수 없으면 불명인 대상·마지막 근거·남은 책임·확인 방법·허용된 후속 경로를 드러내야 한다.

조사로도 결과를 알 수 없을 때, 업무를 더 진행하지 않는 결정과 과거 물리 결과를 알아냈다는 주장은 구분한다. 미해결 상태로 행정적·업무적 처분을 하더라도 필요한 점유·잔여 명령·인계 의무를 별도로 관리해야 한다.

### 10.4 자원 인계

다음 사용자를 허용하려면 그 자원의 성격에 맞는 인계 조건을 확인해야 한다. 물리 자원에는 잔여 명령이 실행될 가능성, 다음 담당자의 제어 가능성, 물품·지지·공간의 상태가 포함될 수 있다. 계산 자원에는 실제 실행의 종료와 적용 상태·사용량의 확인이 필요할 수 있다.

권한의 만료와 실제 점유의 해소를 동일시하지 않는다. 필요한 근거를 확보할 수 없다면 해당 자원 범위의 새 사용을 유보하고 이유와 후속 책임을 남긴다.

반대로 과거 수행의 결과가 미해결이라는 이유만으로 자원 사용을 영구히 막는 것도 이 명세의 목적이 아니다. 별도로 허용된 복구 절차가 현재 상태·잔여 명령·제어 권한·물품 지지 등 필요한 조건을 확인하면, 그 근거를 원 수행에 연결한 복구 처분으로 인계할 수 있다. 이때 과거 결과는 그대로 유지하며 새 업무는 현재 물품 상태와 새 권한을 확인해 시작한다.

## 11. 운영 중 변경과 확장

### 11.1 추가·교체·제거의 공통 조건

변경은 요청한 대상과 목적, 현재 구성, 관련 진행 작업·기능·자원·소비자, 필요한 준비와 전환 조건, 실패 처리, 적용 결과를 가져야 한다.

영향을 받지 않는다고 확인한 작업을 변경 때문에 일괄 종료해서는 안 된다. 영향 범위를 확인하지 못한 경우에는 부족한 사실과 제한할 범위를 명시한다. 전체 무중단을 근거 없이 약속하지 않는다.

### 11.2 현재 작업과 이후 작업

기존 작업에 적용한 계약·설정·담당·결과 해석과 새 작업에 적용할 것을 구별해야 한다. 새 구성이 등록된 것만으로 진행 작업의 의미를 변경해서는 안 된다.

첫 전환 방식의 예는 ‘현재 작업은 기존 담당이 마치고 이후 작업부터 새 담당을 사용’하는 것이다. 이 경우에도 두 실행의 계산 자원·장치 접근·공간 사용이 공존 가능한지 확인해야 한다.

중간 물리 인계가 필요하면 인계 준비·실제 전달·전달 확인·실패 시 책임을 별도 계약으로 제공해야 한다. 같은 기능 이름이나 같은 입력 형식만으로 인계 가능성을 판단해서는 안 된다.

### 11.3 부분 적용과 되돌리기

변경의 일부가 적용됐거나 결과를 확인하지 못한 상태도 관리 대상이다. 시간 초과를 미적용으로 단정해서는 안 된다.

되돌리기 요청은 무엇을 복원할 수 있는지와 이미 발생한 영향을 구분해야 한다. 이전 프로그램·설정 복원만으로 물체·장비·업무 상태까지 되돌아갔다고 처리해서는 안 된다.

### 11.4 기존 모델과의 공존

새 구성요소 경로와 기존 Cell·Host 경로가 같은 물리 자원과 공식 상태에 대해 독립적인 권한을 중복 발급해서는 안 된다. 대응하는 대상·권한 범위·기록의 원본을 확인해야 한다.

한 실행의 관리 주체를 바꿀 때에도 기존 관리와 새 관리가 동시에 소유를 주장하지 않도록 이전·위임·확인의 조건을 정해야 한다. 기존 v1 계약의 추가 필드를 임의로 끼워 넣거나, 새 의미를 같은 wire 계약이라고 주장하지 않는다.

## 12. 장애·복구·부트스트랩

### 12.1 관리 기반의 기동

OS·로컬 부트스트랩은 설치된 신뢰 정책에 따라 최소 관리 기반을 기동·복구할 수 있어야 한다. 시작되지 않은 운영 코어의 승인을 기다려야만 그 코어가 시작되는 순환 의존을 만들지 않는다.

이 권한은 정해진 관리 프로그램과 실행 조건에 한정한다. 관리 기반이 시작됐다는 사실만으로 장비 작업·새 배정·과거 권한의 복원을 허용하지 않는다. 장비 모드·토크를 바꾸는 초기화도 관리 기반 기동의 부수 효과로 숨겨 허가하지 않는다.

### 12.2 재시작과 실제 상태의 대조

실행 인스턴스가 달라졌는지, 호스트·장비·시계 조건이 달라졌는지, 기록과 실제 수행이 일치하는지 확인해야 한다. 저장된 PID·이름·포트만으로 기존 실행의 소유권을 주장해서는 안 된다.

복구 책임은 대조한 사실과 불명인 부분을 제공한다. 권한이 확인된 작업 판단 책임은 업무 정책과 필요한 현장 근거를 이용해 재시도·재개·유보를 판단한다. 변경 절차의 재개는 변경 조율의 책임으로 구분한다.

### 12.3 기록과 저장의 실패

지속 기록이 필요한 일반 명령의 조건을 만족하지 못하면 새로운 관련 효과를 허용해서는 안 된다. 이미 실행됐을 수 있는 행동은 기록 실패 때문에 미실행·취소로 바꾸지 않는다.

조회·진단·회복에 필요한 읽기와 현장 대응은 가능한 범위에서 계속한다. 사전에 정한 로컬 보호 반응은 공통 저장·상위 연결의 성공을 기다리지 않아야 한다. 실제 반응 내용과 효과는 현장 계약과 근거의 범위로 남긴다.

모든 고주기 제어 샘플에 일반 작업과 같은 지속 기록을 요구하는 것으로 해석하지 않는다. 제어 세션의 권한·유효성·순서·종료와 샘플의 사용 규칙을 별도 명세하고, 이를 일반 물리 명령의 기록 의무를 피하는 우회로 사용하지 않는다.

보존·압축·삭제 정책은 중복 요청의 식별, 미완료 책임, 결과 해석에 필요한 근거를 어떻게 유지하는지 명시해야 한다. 기록 손실이나 복원으로 연속성을 잃으면 그 사실을 표시하고, 과거와 같은 권한이 유지된 것으로 가장하지 않는다.

### 12.4 사람의 판단과 개입

사람의 확인은 행위자·대상·관측 범위·시점·절차가 있는 별도 근거로 기록한다. 일반 확인 버튼으로 native 성공이나 장비 관측을 만들어서는 안 된다.

업무가 사람의 인수 확인을 최종 조건으로 정의할 수는 있다. 이 경우 권한 있는 사람의 확인을 그 범위의 업무 근거로 사용하고, 자동 장비 관측으로 위장하지 않는다. 예정된 수령과 비정상 복구 개입도 구분한다.

수동 조작이 기존 사실·점유·권한 조건을 바꿨다면 재개 전에 필요한 범위를 다시 확인한다. RX가 감지할 수 없는 개입은 그 제한과 필요한 운영 절차를 명시한다.

### 12.5 단절과 여러 운영 영역

각 주체의 부팅·실행·시계 영역과 권한 범위를 구분해야 한다. 원격 관측·권한을 이용하려면 신선도·시간 불확실성·지연·중복·순서·만료·재연결의 조건을 명세해야 한다.

단절 중 유지할 로컬 수행은 사전에 허용된 범위와 현재 확인 가능한 조건에 따른다. 연결 상실을 근거로 다른 주체에게 같은 충돌 자원의 사용 권한을 자동 이전해서는 안 된다.

재합류는 연결 성공에 더해 작업·실행·점유·구성·권한의 대조를 포함한다. 시간 동기화 또는 시계 이름 일치만으로 이러한 연속성이 확보됐다고 판단하지 않는다.

이 절은 다중 영역에서 필요한 의미를 요구한다. 현재 같은 주 컴퓨터·단일 Runtime을 대상으로 한 v1 계약이 이미 이 범위를 충족한다고 선언하는 것은 아니다.

### 12.6 복귀 가능한 운영

복구를 위한 필수 정보와 정당한 권한이 확보되고 해당 조건이 만족되면 재개를 판단할 수 있는 절차가 있어야 한다. 미결을 보존하는 구현이 복귀에 필요한 근거를 수집하거나 사용할 경로를 없애서는 안 된다.

과거 결과의 확정, 현재 자원의 복구, 새 업무의 허용은 독립적으로 판단한다. 따라서 과거 결과를 미해결로 유지하면서도 검증된 복구 처분과 현재 조건에 따라 새 업무를 진행할 수 있어야 한다. 실제 복구 능력이나 필요한 근거가 없는 경우에는 이를 가능하다고 표시하지 않는다.

대기·거절·불명이 장기간 이어지면 담당 주체와 부족한 조건, 확인·개입·지원 제외·해결 불가 처분 중 가능한 다음 경로를 보여야 한다. 수치 목표와 자동화 수준은 적용 범위별로 정하며 근거 없이 즉시·무조건 자동 복구를 보장하지 않는다.

## 14. 명세 완결과 남은 결정

### 14.1 개념 명세의 완료 기준

선언한 지원 범위 안에서 독립 작성자가 다음을 일관되게 설명할 수 있어야 한다.

1. 무엇이 등록되고 실행되며 어떤 신원과 책임이 지속되는가.
2. 각 단계가 허용하는 행동과 아직 허용하지 않는 행동은 무엇인가.
3. 판단에 필요한 사실은 누가 제공하고 최종 판단·집행은 누가 맡는가.
4. 어떤 근거로 어느 범위의 결과·지원·인계를 주장할 수 있는가.
5. 변경·상실·불명 뒤 무엇이 남고 어떤 경로로 복귀·처분하는가.
6. 무엇을 공통으로 제공하고 무엇을 작성자·현장 계약으로 남기는가.
7. 기존 규범과의 차이·개정·지원 범위가 무엇인가.

같은 상황에서 여러 정책 선택이 가능할 수 있다. 허용되는 선택의 범위와 반드시 지킬 규칙이 같은 의미로 해석되어야 한다. 하나의 결정 알고리즘이나 실행 배치만 가능해야 한다는 뜻은 아니다.

### 14.3 개념 검토와 실행 검증의 구분

이 문서의 검토는 의미·책임·규칙·사례의 일관성을 확인한다. 실제 구현의 계약 준수, OS 정책의 집행, 장비·부하·장애 상황의 동작은 별도의 검증이 필요하다.

기존 시험 통과 수·과거 모의 사례·문서량을 이번 명세의 구현 완료 근거로 사용하지 않는다. 반대로 실제 장비의 개별 값이 아직 없더라도, 그 값이 어떤 판단에 필요한지와 부족할 때의 처리 의미는 명세할 수 있다.

## 16. 첫 검토에서 사용할 짧은 기준선

**RX가 제공할 공통 약속:** 작성자는 기능과 성립 조건을 제공하고, RX는 참여·실행·작업·자원·권한·상태·변경·복구의 공통 운영 규칙을 제공한다.

**항상 남겨야 할 구분:** 관측과 판단, 접수와 완료, 실행과 업무, 업무 종결과 자원 인계, 과거 기록과 현재 권한, 지원 선언과 적용 근거.

**처음 대조할 장면:** A가 현재 작업을 수행하는 동안 B를 추가해 이후 작업을 넘긴다. B의 조건 미충족, A의 응답 상실, 관측 갱신, 관리 기반 재시작을 차례로 적용한다.

**검토 질문:** 각 장면에서 허용되는 행동과 금지되는 행동, 필요한 근거, 최종 판단·집행 주체, 남는 책임을 문서만으로 설명할 수 있는가.

이 질문에 답하지 못하는 부분은 관리자의 이름이나 구현 기술로 덮지 않고 개념·규칙·지원 범위의 미결로 남겨 수정한다.
