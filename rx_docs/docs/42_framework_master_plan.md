# 42 RX 프레임워크 마스터 플랜 — 탄탄한 상주 코어 위의 패키지 플랫폼

기준일: 2026-09-29. **사용자 승인 계획.** 이 문서는 [프로젝트 목표](01_product_definition.md)를 이루기 위한 전체 작업 순서, 단계별 종료 기준, 결정 사항을 정한다.

2026-10-01 현황 조사에 따른 [세부 개발 계획](implementation/framework_delivery_plan.md)을 추가했다.
사용자는 첫 소프트웨어 초안에 다중 운영 영역을 포함하고, 단절 중 사전 승인된 로컬 작업을 제한적으로
계속하며, 완료 조건·의존성을 먼저 정하도록 선택했다. 따라서 아래 Phase 7의 다중 영역 항목은 첫
소프트웨어 RC의 필수 범위로 앞당긴다. 아래 Phase/버전 표는 이전 계획의 추적 기록으로 유지하며,
현재 작업 배정과 선후관계는 세부 계획 W00–W24를 따른다. 물리 검증은 후속 미완 요구로 남는다.

이 문서는 순서와 기준을 정할 뿐이다. 구현 완료나 검증 결과를 선언하지 않는다. 현재 구현·검증 상태의 기준은 [초안 인계](implementation/draft_handoff.md)와 [핵심 미결](implementation/critical_open_items.md)이다. 실물 설비는 NOT_COMMISSIONED 상태를 유지한다.

2026-10-01의 상주 프레임워크 초안 완성 작업은 [실행 모델](45_resident_framework_execution_model.md)과
[완료 원장](implementation/resident_framework_completion.md)으로 추적한다. 아래 단계와 품질 게이트를 축소하지 않으며,
모델 기준안·구현·실행 검증을 별도로 판정한다. 릴리스 버전 번호는 단계 완료 증거가 아니다.

## 1. 목적과 소개

**목적 (사용자 확정)**

> 서로 다른 로봇·설비·소프트웨어 기능을 공통된 방식으로 연결하고 지속적으로 운영할 수 있는 RX 상주 프레임워크를 만든다.
> 개발자가 반복되는 통합·상태 관리·권한·진단·복구를 매번 다시 구현하는 부담을 줄여, 자기 기능과 업무에 집중하게 한다.
> 참여자가 추가되거나 교체되어도 전체 작업의 책임과 결과가 이어지게 한다.
> 이를 바탕으로 작은 현장부터 여러 운영 영역에 걸친 로봇 협업 서비스까지 개발 자산을 재사용하며 확장한다.

**소개 문장**

> RX는 독립적으로 개발된 로봇·설비·소프트웨어 기능을 공통 계약으로 통합하는 Linux 기반 상주 프레임워크다.
> 구성요소의 실행과 변경을 관리하면서 작업·자원·권한·결과·복구의 연속성을 유지한다.
> 이로써 이기종 협업 시스템의 개발·통합·운영 부담을 줄이고 기능과 서비스의 재사용을 지원한다.

**상주성의 뜻**
- 공통 운영 체계와 남은 책임이 개별 프로그램의 수명보다 오래 유지되는 성질이다.
- 모든 기능을 항상 실행한다는 뜻이 아니다.
- 관리 도구의 접속이 끊기거나 구성요소를 종료·교체해도 등록 정보, 진행 중인 작업, 점유 자원, 확인되지 않은 결과, 복구 책임은 이어진다.

## 2. 형태 — 코어 위에 패키지를 쌓는 플랫폼

ROS 2가 코어 위에 패키지를 개발하듯, RX도 **탄탄한 상주 코어** 위에 장비 연동·기능·공정·앱을 **패키지**로 개발한다. 기존 코어는 새로 만들지 않고 보강한다.

```
 개발자·운영자·상위 서비스
        │  rx CLI · SDK(rxclpy/rxclcpp/Rust) · 운영 화면(패키지) · API(HTTP+gRPC, 이벤트 스트림)
┌───────▼──────────────── RX 상주 운영 기반 (코어 배포판) ────────────────────┐
│ 구성요소 관리     : 패키지·등록·능력·의존성·버전·교체, 서명 검증              │
│ 운영 코어         : 작업 신원·자원·권한(fence/grant)·상태·UNKNOWN·인계·증거   │
│ 호스트 실행 관리  : 프로세스 실행·감독·OS 자원(CPU/메모리/장치) 적용·보고     │
│ 지속 기록·진단·복구: journal, 이벤트 구독, 백업/복원, 재시작 연속성           │
│ Host 게이트       : 장비 명령의 최종 관문(권한·결과 불명 판정은 여기에 남음)   │
└───────▲─────────────── 어댑터 프로토콜(외부 프로세스) / 컴파일 플러그인 ─────┘
  패키지 : 장비 어댑터(DYNAMIXEL, MELSEC, ROS 2 JTC …), 비전·계획·AI 기능, BT 실행기, 공정, 운영 UI
  배포판 : 표준 패키지 묶음, ROBOTIS 번들
        │
 로봇 · PLC · CNC · 시설 제어기 / Linux
```

그림의 상자는 책임을 나눈 것이다. 상자마다 프로세스나 컴퓨터가 하나씩 필요하다는 뜻이 아니다. 영상 같은 대량 데이터가 운영 코어를 통과한다는 뜻도 아니다.

**ROS 2와의 대응**

| ROS 2 | RX |
|---|---|
| rcl 코어 | 상주 운영 기반 |
| rclcpp/rclpy | rxclcpp/rxclpy, Rust SDK, 구성요소 선언 API |
| package.xml | 패키지 manifest v3 |
| colcon | 작업공간 빌드 (`rx ws build`) |
| pluginlib | 어댑터 레지스트리 |
| launch | 사이트 구성, supervisor plan |
| ros2 CLI | `rx` CLI |
| rosdistro | RX 배포판 |
| REP | 계약 revision 절차 |

ROS 코어는 통신을 연결하고, RX 코어는 작업 책임을 관리한다. ROS 기반 기능은 RX 어댑터 패키지로 감싸서 참여시킨다.

## 3. RX 기여와 측정

기여는 설계가 지향하는 바다. 상주한다는 특성만으로 새로움이나 효과가 입증되지는 않는다. 그래서 기존 방식(rx_poc)을 기준선으로 삼아 측정한다.

| # | 기여 | 측정 |
|---|---|---|
| C1 | 반복되는 통합·운영 개발을 공통 기반으로 옮긴다 | 새 기능을 연결할 때 작성하는 코드·설정·파일 수와 시간. 코어 수정 0줄 |
| C2 | 여러 기능의 수행을 하나의 업무 완료로 연결한다 | 이기종 두 계열에서 같은 receipt·인계 의미가 나오는가. 전체 작업 완료율 |
| C3 | 실행이 끊겨도 운영 책임을 잇는다 | 결함 주입 행렬에서 결과 불명·인계 보존 비율. 복구 시간 |
| C4 | 운영 중 확장과 교체를 통제 가능한 과정으로 만든다 | "A가 작업하는 동안 B를 추가하고, 다음 작업부터 B에 배정" 시나리오. 변경 영향 보고의 정확도 |
| C5 | 개별 구현이 재사용 자산으로 쌓인다 | 두 번째 가상 사이트에서의 패키지 재사용률. 진단 시간 |

선행기술 비교 대상: Open-RMF, Nav2, Temporal, SkiROS2, RAFCON, FlexBE, Intrinsic Flowstate, Viam, MoveIt Pro, ctrlX, Industrial Edge.

## 5. 단계

각 단계는 종료 기준을 develop CI에서 통과하고, 게이트 기록을 남긴 뒤 다음 단계로 넘어간다. 저장소 간 PR 순서는 rx_docs(계약·결정) → rx-platform → rx-solutions다. platform 변경 뒤에는 SDK 사본을 platform 원본에서 다시 생성한다.

- 원격에 없던 `codex/python-device-skills` 세 브랜치도 같은 방식으로 보존한다.

**0.2 이 계획 기록**

- [후속 방향](00_design_roadmap.md)과 [결정 목록](09_decisions_and_sources.md)을 갱신한다.

**0.3 Python 장비 스킬 작업 통합**
- `feature/python-device-skills`를 세 저장소에 문서 → platform → solutions 순서로 PR한다.
- 미승인 초안 `design_principles.md`는 포함하지 않는다.

**0.4 연구 작업 이식**
- 먼저 [Host 재수용 비교표](implementation/host_readmission_delta.md)를 만든다(2026-09-29 완료). 기준은 develop의 재수용 설계다. 연구 host-rejoin에서는 없는 의미만 흡수하고, 나머지는 폐기 이유와 함께 기록한다.
- 비교 결과에 따라, 이미 검증되고 독립적인 항목만 Phase 0.4에서 이식한다. 재수용 기준으로 다시 설계해야 하는 항목은 Phase 2로 옮긴다. 연구 원본은 로컬 bundle로 보존되어 있다.

### Phase 1 — 코어 헌장과 경계

**코어 헌장** ([43](43_core_charter.md), 2026-09-29): 아래 중 하나에 해당하면 코어다. 해당하지 않으면 패키지다.
- 바꾸면 기존 증거·receipt·계약 hash의 의미가 무효가 된다.
- 틀려도 밖에서 관측되지 않는다. 권한·결과 불명·인계 판정이 이에 해당한다.
- 단일 writer 직렬화나 저장 원자성에 참여한다.
- 규범 필드를 해석한다.

**개념 명세 채택** ([44](44_resident_framework_concept.md), 2026-09-29)
- 사전 연구의 상주 프레임워크 개념 명세(2026-09-23)를 이 저장소로 옮겼다.
- OD01–OD06 확정. Cell은 협업·권한 구성이며 구성요소의 존재 조건이 아니다(OD03). 첫 전환 수준은 다음 작업부터다(OD04). OD07은 Phase 4·6에서 정한다.
- 구성요소 등록의 소유자(OD08): P가 등록 신원·선언·standing을 소유하고 supervisor가 실행 인스턴스·자원 적용 사실을 기록·보고하는 안을 2026-10-01 [실행 모델](45_resident_framework_execution_model.md)의 구현 기준안으로 구체화했다. 과거 사용자 확정으로 소급하지 않으며 이행·검증은 남아 있다.

**Engine 내부 봉합선** (동작 변화 없이)
- 코어 모듈과 cell·production 모듈을 그룹으로 나눈다.
- cell 도메인 port trait을 둔다.
- Cell 구조를 저장 형식 그대로 분리한다.
- 경계 검사를 CI에 넣는다. **구현(rx-platform #47)**: 모듈 52개를 core·cell·change_control 세 그룹에 배정하고, 현재의 역방향 참조 18곳(31회)을 줄이기만 할 수 있는 목록으로 기록한다. 텍스트 경로 분석이며 타입 해석은 하지 않는다.

**종료 기준**
- 헌장과 개념 문서가 승인된다.
- 경계 위반이 0건이다.
- 기존 시험이 모두 통과한다.
- 저장 스냅샷이 바이트 단위로 동일하다.

### Phase 2 — 코어 보강

| 영역 | 내용 |
|---|---|
| 재시작 인수 | A안을 구현한다. "이번 boot에서 재확인"을 따로 두고, 준비되지 않은 상태를 승인 철회와 구분한다. **구현(rx-platform #42)**: Store 소유자 영속, 정책 불변 시 generation 재사용. `Unavailable` 구분은 남음 |
| 재자격 연속 | 정책 등록은 매 boot 재구성으로 유지된다(변경 불필요). 2번 경로(cell_delivery 고정물에서 변경 후 구성 사전 계산) 타당성: 연쇄의 Id는 모두 클라이언트가 정하므로 미리 발급할 수 있다. 걸림돌은 장치 검토 Version digest에 들어간 P 기록 시각이었다. 이 시각이 plan digest → compile input → package → 변경 후 구성으로 전파됐다. **해소(#49)**: digest v2에서 기록 시각을 제외했다. 장치 검토는 릴리스 태그에 없어 호환 경로를 두지 않았다. 2번 경로는 설치 전에 계획한 binding만 다룬다. 설치 뒤에 정한 변경은 1번 경로(새 정책으로 재시작)나 새 설치가 필요하므로 두 경로는 보완 관계다. E2E는 진행 중 |
| 재시작 연속성 행렬 | 재시작 때 잃는 항목을 영속 / 재확인 / 의도적 소멸로 분류하고 시험한다. **조사(2026-09-30)**: 약 65개 항목을 분류했다. 그 과정에서 재시작 뒤 셀이 서비스에 복귀하지 못하는 결함이 드러났다. **수정**: (1) 정상 종료(SIGTERM)가 모든 셀에 남기는 AuthorityRevoked에 해제 경로가 없었고, executor가 같은 프로세스로 재접속해도 출처 없는 AuthorityRevoked를 다시 추가했다. 그래서 정상 재시작마다 셀이 영구히 막혔다. 종료 origin을 기록하고 P만 재시작한 경우의 executor 재접속을 판별하도록 고쳤다(rx-platform #52). (2) 계약에 있는 AbandonRun이 미구현이라, 재시작으로 RecoveryRequired가 된 Run이 변경·구성·재자격 게이트를 영원히 막았다. 진행 중인 작업이 없을 때 운영자가 폐기하도록 구현했다(#53). **남음**: 재시작한 executor의 AuthorityRevoked 해제, 재시작 때 무효화된 작업이 잡고 있는 자원의 격리, store 복원 뒤 이전 generation 제한의 선택 불가, 이전 boot의 대기 중인 자격 배치, 거절된 Arm 전송의 무한 재시도 |
| 중단 없는 writer | 단일 writer 경로의 panic 가능 지점을 없앤다. 명령 단위 오류와 서비스 정지를 구분한다. **구현(#43)**: unwrap 제거, `clippy::unwrap_used` deny, 티켓 TTL 상수 |
| 백업·복원 | 복원하면 store generation을 새로 발급해 Host가 롤백을 감지하게 한다. 모든 버전→최신 업그레이드를 시험한다. **구현(#46)**: `rx-platformd backup/restore`, `rx.store-restore.v1` 기록, 스키마 1–5 업그레이드 시험 |
| 성장 상한 | 무한히 커지는 목록과 전체 prefix 조회를 상한·페이지 단위로 바꾼다. **조사·1단계(2026-09-30)**: 저장소의 prefix 조회가 `LIKE`여서 인덱스를 쓰지 못했고, 모든 조회가 prefix와 관계없이 store 전체 키를 읽었다. 기본키 범위 조회로 바꿨다(rx-platform #51, SDK rx-solutions #67). 관계없는 키 100만 개 옆에서 20행 prefix 조회가 43ms에서 0.012ms가 됐다. **남음**: 자주 호출되는 경로(25ms 감시, 호스트별 100ms 전송, Run 변경마다 checkpoint)가 이력 전체를 읽는 문제는 셀별 live 집합 인덱스로 바꿔야 한다. 누적 Run 1만 개에서 executor 배정이 영구히 실패하는 절벽, Run·ExecutorState 문서 1MiB 한계(스텝 5개면 part 약 800개), fence ack·case retention도 남았다 |
| 이벤트 스트림 | 두 단계로 나눈다. (1) 운영자 BFF의 SSE(`/api/v1/events`): 제어 journal의 변경 알림으로 3초 폴링을 대체한다. 공개 계약이 아니다. (2) gRPC `Journal.Subscribe`/`GetSnapshot` 등록: rx-platform `CONTROL_JOURNAL.md`가 밝힌 공개 매핑(CellJournalRecord·SnapshotEntity, cursor·보존·gap·구독자 상한)이 끝나야 등록한다. 매핑 없이 등록하면 동결 계약 적합성을 주장하는 것이 되므로 하지 않는다 |
| API 수명주기 | 미구현 RPC를 구현 / 삭제 / 예약으로 판정한다. deprecation 절차를 둔다 |
| 관리 축 연결 | 등록·준비·업무 사용을 supervisor와 platform 사이에서 끝까지 연결한다 |
| 호스트 실행 자원 | 실행 요구를 cgroup v2(CPU·메모리)와 장치 접근으로 적용하고 보고한다. 지원하지 않는 요구는 거절한다 |
| **P 재시작 뒤 유지된 Host의 운영 rebind** | P만 재시작하고 Host는 그대로이면 운영 등록이 옛 세션에 묶여 셀이 link를 되찾지 못했다([기록](../references/p_restart_adoption_2026-09-29/README.md)). **구현(#45)**: 재수용이 세션 만료된 같은 boot를 교체, grant 만료 대기, 소비 시 work 재검사, 이력 키에 세션. 실제 이미지 3회 연속 통과([기록](../references/p_restart_rebind_2026-09-29/README.md)) |
| Host 재시작 뒤 복귀 | 무효화 origin 기록을 둔다. **DeviceRestart block 해제 경로**를 만든다. 재기동 Host의 결과를 아는 작업을 정산한다(settlement v2). 모두 재수용 기록을 기준으로 한다([비교표](implementation/host_readmission_delta.md)). **origin·해제 구현(#48)**: 재link(기록된 epoch 이후의 bound link) 뒤 재자격 선택으로만 해제. settlement v2는 남음 |
| 관측 전용 참여 | observation-only binding(P와 Host). 제어 권한 없이 관측만 제공하는 구성요소를 참여시킨다 |
| 시험 신뢰성 | 시간에 의존하는 불안정 시험을 결정적 대기로 바꾼다(예: platformd 기동 8초 타임아웃). **처리(2026-09-30)**: platformd 기동 대기는 준비 완료 또는 서버 종료 신호로 끝나게 했다(rx-platform #50). rx-host 시험의 간헐 실패는 CI 로그상 ETXTBSY였다. 실행 파일을 쓰자마자 exec할 때 다른 스레드의 fork와 겹치는 **제품 경합**이라, 운영 중 bridge 기동도 실패할 수 있었다. exec 실패만 제한 재시도하도록 고치고 Linux 재현 시험을 두었다(rx-solutions #66) |

**품질 게이트**
- 불변식 30개 모두 의미 시험으로 커버한다.
- 속성 기반 시험을 둔다.
- 결정적 시뮬레이션에서 10k seed 동안 불변식 위반 0건이어야 한다.
- 결함 주입 행렬을 전수 실행한다.
- 처리량 기준값과 24시간 soak 결과를 남긴다.

### Phase 3 — ROS식 확장 모델

**어댑터 프로토콜**
- Host 어댑터 계약을 버전 붙은 외부 프로세스 프로토콜로 만든다.
- 연결이 끊기거나 응답이 불명이면 Host가 결과 불명으로 판정한다.

**열린 레지스트리**
- 닫힌 backend 목록을 레지스트리로 바꾼다.
- 외부 프로세스 어댑터와 컴파일 플러그인을 모두 지원한다.
- 새 backend를 추가할 때 코어 수정은 0줄이어야 한다.

**구성요소 선언 API**
- 선언 항목: 능력, 입력·결과, 의존성, 실행 자원, 권한, 준비 조건, 종료·교체 시 확인할 것.
- 등록은 작업 배정과 독립이다.

**그 밖의 작업**
- 패키지 manifest v3(실행 코드와 빌드·실행 의존성)를 만든다.
- 서명된 supervisor recipe 패키지를 받게 한다.
- 통합 `rx` CLI를 만든다: 패키지 생성·빌드·서명·설치, 작업공간 빌드, conformance.
- conformance 도구와 템플릿을 제공한다.
- 클라이언트 라이브러리에 구독과 고수준 API를 추가한다.

**수락 시나리오**
- A가 작업하는 동안 B를 등록하고 준비를 확인한다.
- 다음 작업부터 B에 배정한다.
- A의 작업과 기록은 유지되고, 영향이 없는 작업은 계속 진행된다.

### Phase 4 — 표준 패키지·배포판·rx_poc 동등성

- 표준 어댑터: DYNAMIXEL, MELSEC, ROS 2 JTC.
- 표준 기능: Python 스킬 실행기, 공정·BT 실행기, 운영 UI(이벤트 스트림으로 전환).
- ROBOTIS 번들: 모의 범위에서 완결한다.
- rx_poc 기능 동등성 표를 만든다. 대상 예시는 기존 공정 이식, 관측 좌표 전달, 그리퍼, 고수준 동작 API다. 각 항목을 패키지 / 코어 / 폐기로 판정한다.
- **종료 기준**: 깨끗한 환경에 한 명령으로 설치된다. 설치 시간과 작성 비용을 기록한다.
