# 현황 기반 RX Framework 세부 개발 계획

작성일: 2026-10-01. **계획 문서이며 구현 완료 기록이 아니다.**
사용자가 요구한 전체 소프트웨어 초안, 다중 운영 영역, 단절 중 사전 승인된 로컬 작업 계속 수행,
완료 조건·의존성 우선의 일정 수립을 반영한다. 작업 순서와 기술 선택은 아래 현황 조사에서 도출한
구현 계획이다. 이 문서만으로 기존 규범·wire·저장 형식을 변경하지 않는다.

상위 방향은 [마스터 플랜](../42_framework_master_plan.md), 기능 기준은
[WF01–WF17](../46_workflow_product_experience.md), 상주성 기준은
[RF01–RF14](resident_framework_completion.md)다. 아래는 그 세부 실행계획이며 새 제품 목표가 아니다.

## 1. 먼저 확인한 출발점

원격 develop을 직접 조회한 기준은 P `cc9829197fe8435ccd0195ae20b23e22260a3487`,
S `3e72f45430600652291e20fb089380192bb000c5`, D `4e30227202b99300abc71747f87b36fe41e62088`다.
P/S의 해당 develop CI 성공도 확인했다. 기본 체크아웃은 각각 15/15/38커밋 뒤에 있으므로
기본 폴더의 파일만 읽거나 그 폴더에서 빌드한 결과를 최신 구현이라고 취급하지 않는다.

전체 Rust workspace, 전체 브라우저 E2E, native ROS/BT 및 장시간 운전은 이번 조사에서 재실행하지 않았다.
기존 CI/통합 장면 근거는 해당 커밋과 범위로만 사용한다.

R7 실패의 직접 경로는 새 recovery reader barrier가 application의 control-journal Tracking
transaction에 전달되지 않아 기본 unsupported 메서드로 가는 것이다. 이 수정만으로 R7의
전송·source 확인·새 실행 경로가 완료되는 것은 아니다.

운영 코어의 별도 공백: case의 ReadyForRestart 전이 경로, 복원된 epoch를 Host 최대값과 대조하는
OI11/OI17 경로, 일반 공개 확장/영역 간 프로토콜. 불변식 추적표의 P 21 declared/9 uncovered,
S 7 declared/23 uncovered는 **검토된 시험 연결 상태**이며 제품 완성률이나 결함 개수가 아니다.

## 2. 제품 완료 기준과 경계

첫 RC의 사용자 경로는 **Task 정의 → 액션 그래프 → 대상/자원·값/출처·로봇 적합성 → 검증/Preview →
불변 버전 게시 → 설치/실행 → 관찰/개입/복구 → 변경/업그레이드**다. 각 단계의 결과를 다음 단계가
같은 식별자와 버전으로 소비해야 한다. 외부 작성자도 코어 수정 없이 참여할 수 있어야 한다.

- 주 사용자는 통합 개발자와 운영자다. 개발자 정의와 운영자 조합/실행을 구분하고 서버 권한으로 집행한다.
- 액션 그래프가 주 화면이다. 정의 편집, 오류, 값의 출처, 운영 상태는 그래프 문맥에서 접근한다.
- 첫 초안의 Preview는 실행 의미·모의 장비 결과를 검증하는 trace다. 3D 물리 시뮬레이터 신규 개발은 포함하지 않는다.
- 다중 영역은 독립 P 원장/저장소/실행 호스트를 가진 두 영역과 세 번째 영역 연쇄를 검증한다.
  독립 프로세스 재현 시험에 더해 분리 Linux 호스트 간 전송·단절도 확인한다.
- 물리 검증 RF14, 도시 규모 성능 실증, BT 자동생성 연구는 후속이다. RF14는 전체 제품의 미완 항목으로 남는다.
- PG07 다섯 프로젝트와 클라이언트 라이브러리는 필수다. 일개미·집개미는 제외한다.
- 현장 주소·TCP·힘·속도·실제 timeout을 추정하지 않는다. 시험값은 별도 SIMULATION profile로 명시한다.
- UI/코드 저장소의 공개 언어 정책은 현재 영어를 유지한다. 사용자 작성 공정명은 한국어를 사용할 수 있다.

## 3. 구현 경계와 계약 결정

| 책임 | Platform | Solutions |
|---|---|---|
| 저작·카탈로그 | 버전/CAS/접근 권한/게시 기록, 공통 계약 원본 | 정의 UI·카탈로그 패키지·편집기·SDK |
| 계산·검증 | 서버가 검증한 정확한 입력/정의 버전과 결과를 보존 | 공통 순수 resolver/컴파일 경로를 저작/Preview에서 재사용 |
| 공정 실행 | 현재 작업 신원·권한·결과·자원 의무를 소유 | 공정 제어 의미·Skill 실행·장비 프로토콜 집행 |
| 상주 관리 | 등록·배정·정산·변경의 공식 결정 | Supervisor의 프로세스/OS 자원 집행과 관측 |
| 영역 간 협업 | 영역별 결정·위임/인계 상태·원 요청 기록 | 인증 전송/재전달·현장 실행·통합 UI |

공통 타입은 P 원본에서 S SDK로 생성한다. 공정 이름·품목·지그·로봇 모델은 코어가 아닌 패키지/현장 자료다.
별도의 권한 DB나 UI 전용 실행 엔진을 추가하지 않는다. 기존 wire를 깨는 변화는 기존 v1.1 revision
절차에 따라 의미·호환성·이행·hash를 먼저 명시한다. optional binding의 변화는 그 binding revision으로 다룬다.

### 저작과 실행의 단일 의미

- 새 Workflow source는 명시적 Node/Port/Edge와 Branch/Parallel/Loop/Call의 제어 의미를 갖는다.
  일반 순환 연결은 거절하고 반복은 Loop로 표현한다. 병렬 분기/합류와 중첩 범위를 검증한다.
- 현재 ProcessSource는 그대로 읽고 실행한다. 새 저작의 편집 변환은 복사본과 변환 보고서를 만들며
  원본/기존 패키지 digest를 바꾸지 않는다. 표현 손실이 있으면 자동 변환을 거절한다.
- 좌표/뷰 상태는 실행 소스와 분리한다. 실행 IR에서 원 Node/Edge 및 하위 흐름/반복 회차를 역추적한다.
- Preview와 운영은 같은 검증/컴파일/제어 흐름 경로를 사용하고 장비 provider만 다르게 연결한다.
- ParallelAny는 첫 성공 이후 다른 분기의 취소/종료 의무를 보존한다. 충돌 자원은 종료/정산 전 재사용하지 않는다.
- Loop는 횟수 또는 조건과 유한 상한/기한을 요구한다. Wait는 시간/조건/이벤트/자원을 구분한다.
- Event는 실행·노드 방문·발신자 범위에 연결하고 중복/오래된 이벤트를 소비하지 않는다.

### 정의·값·선정

- TaskDefinition, Object Type/Model, Resource Type/Model/Instance, Property/PropertySet,
  Capability, SkillMapping은 별도 개념이며 정확한 revision 참조로 묶는다.
- resolver 입력은 정의 버전, 대상, 자원 인스턴스, 허용 Override, 실행 입력이다. 출력은 값/단위/출처/
  적용 규칙/누락·충돌과 Node/Port/Property 위치다. 임의 JavaScript/Python eval은 사용하지 않는다.
- Property마다 허용 출처·우선순위·덮어쓰기 가능 여부를 정의한다. 순환 상속과 같은 우선순위의 모순은 오류다.
- Task 제약과 로봇 능력/Skill 구현/현재 준비를 각각 판정한다. 선언된 사양만으로 실행 권한을 만들지 않는다.
- 자동 후보 선정은 가능/제외 이유를 설명하는 단계와 실제 자원 확보/배정을 분리한다.
- 실행 시 바인딩하는 대상은 실제 입력 수신 후 재검증한다. 게시 당시 미정인 값을 통과로 고정하지 않는다.

### 운영·정책·분산

- Draft, Published, Archived와 설치 적용/활성 버전/실행 상태를 분리한다. 게시가 장비 시작이 되지 않는다.
- Retry는 알려진 미실행 또는 해당 adapter가 보장하는 반복 가능 범위에서 제한 실행한다.
  결과 불명은 원 operation을 조회·정산한다. Rebind/Reassign은 기존 책임을 지우지 않는다.
- Runtime Guard는 조건 상실을 대기/보류/개입으로 연결한다. 운영자 확인을 물리 완료로 해석하지 않는다.
- 영역 참조는 영역 신원과 원 로컬 ID를 함께 보존한다. 기존 UUID를 다시 발급해 이력을 끊지 않는다.
- 영역별 단일 writer를 유지한다. 전역 합의 클러스터나 공동 writable DB는 첫 RC에 추가하지 않는다.
- 영역 간 프로토콜은 기존 mTLS/gRPC 기반을 확장한다. 요청/인계 ID, 출처·대상 영역, 내용 digest,
  위임 범위/세대/유효 조건, 원 receipt를 지속 기록하고 원 요청 조회로 유실을 복구한다.
- 단절 중 승인된 로컬 작업만 계속한다. 권한 만료·철회 확인 불가가 무제한 권한이 되지 않으며,
  미확인 인계/자원은 새 소유자에게 중복 배정하지 않는다. 재시작은 저장된 grant를 부활시키지 않는다.
- 원격 유지보수는 조회·증거 수집·변경 제안/승인·적용·확인을 구분한다. 원격 접속권과 장비 운전권은 별개다.

## 4. 작업 묶음과 의존성

이미 확인한 완료 조건의 선행 작업이다. 기능 하나를 이유로 관련 없는 전체 재설계를 시작하지 않는다.

## 6. 대표 공정과 검증 데이터

대표 시연은 0층 레이저 열처리다. CNC 그림은 교환 순서의 참고이며 가공기 제어 의미는 별도다.

- 듀얼: 다음 소재 취출 → 별도 회전 정렬 → 가공 완료 대기 → 다른 채널로 완성품 인출 → EE 전환 →
  청소/삽입/착좌/Clamp/Release → 후퇴/닫힘/가공 시작 → 완성품 배출.
- 싱글: 완성품 인출/배출 → 다음 소재 취출/별도 회전 정렬 → 삽입/착좌/Clamp/Release → 후퇴/닫힘/시작.
- 버퍼 싱글은 명시적 버퍼 자원·지지/점유 조건이 있을 때만 선택 가능하다. 기본 설치가 실제 버퍼를 가정하지 않는다.
- 공통 회전 정렬: 준비/점유 → 배치/안착 → 방향 검출 → 장비 회전 → 정렬 확인/정지 → 재파지.
  회전 중 파지 유지/해제는 현장 미확정 항목으로 남긴다.
- ECC_51/ECC_99/CVR_F/FLANGE_L/FLANGE_R와 14/17형: 10종 해석, CVR_F 앞/뒤 별도 setup,
  12 setup 행/8 지그 변형의 현재 자료 해석을 유지한다. 핑거 색과 형 번호를 부품번호/치수로 확정하지 않는다.
- 최초 빈 설비 투입, 정상 반복, 마지막 배출, 품목 교체, 정렬 실패, 착좌 실패, 파지 채널 경합,
  응답 유실, 중단 후 복귀를 각각 시험한다. 투입 소재와 완성품 신원을 분리한다.
- 다중 영역 시연의 공급/처리/회수는 가상 시험 구성이다. 실제 현장 네트워크·조직 구성을 주장하지 않는다.

## 7. 개발·검증·릴리스 운영

### 작업의 완료 조건

묶음마다 구현 전에 변경 책임/입출력/오류/기존 호환성/양성·음성 시험을 적는다. D 계약 원본 → P →
생성 SDK/S 순서로 통합하고, CI와 교차 저장소 검증을 같은 변경 조합으로 확인한다.
지원 경계가 다른 모의/실물·source/registered 경로의 결과를 합치지 않는다.

상태는 **계획 → 구현 중 → 로컬 검증 → 통합 검증 → 배포 검증**으로 기록한다. 문서/형식 검사,
유닛 테스트, browser E2E, 분리 프로세스/호스트, 설치/장시간 검증을 따로 표시한다.
UI가 저장한 소스로 결과를 재현하고 실패 후 처리까지 확인해야 사용자 기능을 완료로 세며,
통합되지 않은 WIP나 시험 개수를 제품 완료율로 쓰지 않는다.

### 안정성 수락 기준

- 원 operation/인계의 효과 중복, 미확인 의무의 자동 삭제, 권한 없는 명령 수락은 허용하지 않는다.
- 각 durable 경계의 commit 전/후 실패·응답 유실·재시작, 잘못된 주체/세대/내용·시간을 시험한다.
- 품질 게이트의 30개 불변식은 책임별 의미 시험으로 대조한다. 테스트명 등록만으로 닫지 않는다.
- 결정적 10k seed와 24h soak를 수행한다. 부하/메모리/저장 증가/지연·복구시간은 조건과 함께 기록하고
  제품 지원 한계를 그 결과로 명시한다. 근거 없는 처리량/SLA 수치를 약속하지 않는다.
- 서로 다른 두 장비 계열과 두 번째 가상 사이트에서 공통 의미·코어 수정 0·작성/진단 비용을 측정한다.
- native 또는 분리 Linux 호스트 자원이 없으면 해당 증거는 외부 대기로 남기고 RC 완료를 선언하지 않는다.

### 범위와 일정 통제

초기 세 개발 묶음(W01–W03)의 설계/구현/검증/재작업 시간을 기록한 뒤 일정 범위를 산정한다.
고정 날짜는 아직 없다. 현재 통과한 기능을 기준으로 전체 범위를 줄여 추정하지 않는다.
추가 요구는 기존 WF/RF/PG의 하위 작업인지 새 범위인지 먼저 판정하고, 새 범위라면 영향과
밀리는 작업을 함께 기록한다. 임의의 새 매니저/DSL/DB·대규모 리팩터링을 편의상 선행하지 않는다.

각 묶음은 실행 가능한 화면/명령, 저장된 결과, 실패 처리, 정확한 미완 경계를 보여준다.
최종 배포는 소스 고정 → 해당 소스 안정성 검사 → 동일 소스 패키징 → 새 환경 재현 순서다.
제품 초안 RC는 W00–W24의 소프트웨어 수락이 모두 충족될 때이며 현장 제품 완료 RF14와 구분한다.

신규 source/IR 실행 지원은 W09–W12에서 명시적으로 검증한다.

W01 설계는 다음 세 가지를 고정하고 구현 단계의 계약 시험으로 검증한다.

1. 기존 ProcessSource를 보존하면서 새 포트 그래프를 저장/검증/실행할 계약과 변환 예시.
2. Task/Object/Resource/Property/Skill의 정확한 참조와 resolver 결과 계약.
3. 복구·영역 간 위임에서 기존 원장/신원/권한을 재사용하는 경계와 필요한 추가 기록.

W01의 종료는 개념 문서의 분량이 아니라, 듀얼/싱글 레이저 예시와 실패/병렬/영역 간 인계를
이 계약으로 표현하고 UI 입력→서버 자료→실행 의미→결과 위치를 빠짐없이 대응시킬 수 있는지로 판정한다.
