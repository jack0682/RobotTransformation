# 45. RX 상주 프레임워크 실행 모델

기준일: 2026-10-01. 개념 모델 revision 1, **구현 기준안·검증 미완**.
사용자가 요청한 상주 프레임워크 초안을 완성하기 위해 [개념 명세](44_resident_framework_concept.md)의
OD08·RR01–RR03을 구체화한다. 아래 결정은 이번 작업에서 채택한 설계안이며, 과거의 사용자 확정으로
소급하지 않는다. 문서 작성·상태 이름·구조 검사만으로 모델 또는 제품의 완성을 선언하지 않는다.

기존 공통 계약 v1.0·셀 계약 v1.0과 그 manifest는 그대로 유효하다. 이 문서는 아직 새로운 wire·DB
형식을 동결하지 않는다. 구현별 revision·이행·반례와 SDK 영향은 [완료 원장](implementation/resident_framework_completion.md)에
연결한다. 충돌하는 기존 규칙을 문서상의 새 이름으로 우회하지 않는다.

## 1. 완료할 대상

RX는 개발자가 제공한 로봇·설비·관측·계산·계획 기능을 받아, 그 기능의 존재와 실행보다 오래
유지되는 신원·업무·자원·변경·복구 책임을 관리한다. 독립 작성자는 코어를 수정하지 않고 지원되는
확장 계약으로 기능을 제공하며, 운영자는 같은 설치를 계속 관리할 수 있어야 한다.

초안 완료에는 모델, 구현, 작성·운영 경로, 검증이 함께 필요하다. 매번 새 모의 설치를 만드는
demo, 프로세스 생존, 설치 성공, 과거 CI 통과는 같은 설치의 지속 운영이나 프레임워크 완결의 증거가 아니다.
도입·유지보수 제품이라는 목적은 유지한다. 견적·현장 책임·지원 약속을 소프트웨어만으로 자동 충족했다고
주장하지 않으며, 현장 적용 및 물리 검증 게이트도 삭제하지 않는다.

각 전이는 요청 주체, 기대 revision, 현재 조건, 최종 판단자, 집행자, 지속 기록, 응답 유실 후 조회,
부분 실패의 남은 의무, 허용된 다음 행동을 가져야 한다. 모르는 항목은 완료나 성공으로 채우지 않는다.

## 2. 대상과 신원

| 대상 | 지속되는 신원·내용 | 별도로 변하는 것 |
|---|---|---|
| 패키지 릴리스 | 발행자·내용 digest·계약·지원 조건 | 설치 위치, 등록 대상, 실행 인스턴스 |
| 구성요소 형식 | 제공 기능·입출력 의미·수명 효과·의존·요구 계약 | 구현 릴리스와 현장별 설정 |
| 등록 구성요소 | 설치/운영 영역 안의 component ID, 수용한 선언 revision, provenance | 활성 설정 revision, 등록 standing, 실행 배정 |
| 실행 인스턴스 | instance ID, component ID, 정확한 package/configuration/binding revision | PID·프로세스 관측·준비·업무 사용 판단 |
| 계산 호스트 | host ID, 지원 자원 정책과 신뢰 연결 | OS boot, manager incarnation, 실행 소유 관측 |
| 의존 결합 | consumer·provider·기능·사용 단계·의미/버전·결합 revision | 제공 인스턴스, 관측 freshness, 재평가 결과 |
| 작업과 수행 | task/run ID, operation ID, 원 요청과 의도 | 전송 시도, 수행 지식, 결과, 자원 의무 |
| 자원 요구·점유 | canonical resource ID, 요구 의미, claim ID와 holder | 예약/실제 점유 상태, fence, 해제·인계 근거 |
| 관측·근거·판단 | 출처와 내용·대상·범위·관련 전이 | 유효 시각, source generation, 소비 가능성 |
| 변경·복구 건 | request ID, before/after revision, 대상 closure, 책임자 | 단계, 관측된 적용, 미해결 의무, 다음 조치 |

Cell은 업무 협업·권한 구성이다. 관측·계산 구성요소의 등록과 존재에 Cell 생성을 강제하지 않는다.
Cell에 배정될 때만 해당 협업 구성과 업무 조건을 추가로 확인한다. 한 host, process, robot, cell,
물리 보호 구역을 같은 경계로 가정하지 않는다. restart는 새 instance/boot이며 같은 component ID를 지울 이유가 아니다.

## 3. 공식 상태와 집행 책임 — OD08

| 책임 | 공식 상태의 최종 갱신자 | 사실·집행 제공자 |
|---|---|---|
| 선언 수용·등록 신원·standing·활성 구성 | 해당 운영 영역의 Platform 단일 writer | 작성자, 패키지 검증기, 운영자 |
| 실행 배정의 승인과 업무 사용 조건 | Platform | Supervisor의 실행/자원 사실, 의존 제공자, 외부 자격 판단 |
| 실제 프로세스 생성·소유·종료 | 해당 계산 호스트의 Supervisor | OS와 소유한 process handle/boot 관측 |
| 협업 자원 예약·권한·작업 결과 | Platform | Host의 원본 전달·결과·점유 기록 |
| 장비 명령 직전 허가·로컬 조건 집행 | Host gate | 어댑터·제어기·현장 보호 책임 |
| 공통 상태의 표시·요청 전달 | 원장을 소유하지 않음 | UI·CLI·SDK·상위 서비스 |

Supervisor의 `registration.db`는 이행 전의 등록 자료와 호스트 실행 기록을 보존한다.
등록 신원을 Platform으로 옮길 때 새 UUID로 바꿔 역사를 끊지 않는다. 구 원장의 **등록·선언 쓰기만** 차단하고,
실행 관측의 기록은 유지한다. 수용한 mapping/수정 revision/old digest를 기록한 뒤 새 등록 경로의 쓰기를 연다.
수입 완료를 확인하지 못하면 양쪽 등록 쓰기를 모두 활성화하지 않는다. 이 제한을 모르는 구버전 writer가
살아 있으면 이행을 확정하지 않는다. 이미 시작된 프로세스의 소유권은 이 DB 수입으로 만들어지지 않는다.

Platform이 사용할 수 없을 때 Supervisor는 기존 실행의 관측·로컬 보호·허용된 종료를 계속할 수 있지만
새 등록, 새로운 업무 배정, 과거 grant의 부활을 독자적으로 승인하지 않는다. OS bootstrap의 관리 프로그램
기동 권한은 사전 설치된 신뢰 정책에 한정한다. 장비 모드나 토크를 바꾸는 초기화는 별도의 효과 계약과
Host gate를 거쳐야 한다.

## 4. 독립된 상태 축과 관찰

| 축 | 최소 상태 | 원칙 |
|---|---|---|
| 릴리스 수용 | 미수용·수용·폐기됨 | 서명 수용은 사용 허가가 아님 |
| 등록 | 수용됨·신규 사용 정지·퇴역 | 퇴역해도 과거 작업·의무·근거는 남음 |
| 실행 | 미배정·준비·시작 중·실행 관측·종료 요청·종료 확인·불명 | timeout/PID 부재만으로 종료 확인 금지 |
| 기능 준비 | 미평가·불명·불충족·충족·미지원 | 살아 있음과 기능 준비를 구분 |
| 업무 사용 | 미평가·거절·현재 범위에서 허용·만료/철회 | task/role/context/instance에 묶인 판단 |
| 수행 지식·결과 | 기존 계약의 별도 축 | UNKNOWN을 임의로 실패·미실행으로 바꾸지 않음 |
| 자원 의무 | 예약·점유·해제 대기·격리·해제 확인 | 논리적 예약 취소와 실제 인계는 다름 |
| 변경·복구 | 제안·준비·적용 중·확인 중·확정·거절·불명/주의 필요 | 과거 결과를 바꾸지 않고 현재 복귀 가능 |

위 상태 이름은 논리적 의미다. 기존 wire enum을 몰래 대체하지 않는다. 각 공개 조회는 현재 사실인지
과거 관측인지, revision과 관측 시각/clock domain, 부족한 조건, 담당자와 가능한 다음 요청을 제공한다.
불명·거절 뒤 아무 행동도 할 수 없는 상태라면 모델의 복구 경로가 미완인 것이다.

## 5. 참여에서 퇴역까지

1. **수용**: 릴리스·선언·지원 조건을 확인하고 요청을 지속 기록한다. 같은 키/같은 내용의 유실 응답은
   같은 수용 기록으로 돌아간다. 같은 키의 다른 내용은 거절한다.
2. **등록**: Platform이 stable component ID와 선언 revision을 기록한다. 아직 process나 Cell이 없어도 된다.
3. **결합**: 기능과 소비자가 사용할 의존·자원·설정 revision을 해석한다. 실행 의미가 없는 descriptor도 조회 가능하다.
4. **실행 준비**: 전체 요구 묶음의 수락과 호스트 적용을 §6에 따라 수행한다. 불완전한 준비로 업무를 시작하지 않는다.
5. **시작·준비 관측**: 새 instance를 명시 배정하고 Supervisor가 실제 생성/소유를 기록한다. 준비는 해당 기능의 계약으로 판단한다.
6. **업무 사용**: 현재 task/role/context와 의존·자원·장비 조건을 대조한 뒤 허용한다. 원본 결과·인계는 Host gate와 P 원장으로 연결한다.
7. **변경**: 현재 업무를 유지할 범위와 다음 업무부터 적용할 구성을 명시하고 §8을 따른다.
8. **정지·퇴역**: 새 배정을 막고 실행·진행 수행·결과 소비·자원 의무를 대조한다. 필요한 의무가 남으면 퇴역 요청을 보류하고 조사 경로를 제공한다.
   package 파일 제거 후에도 과거 의미를 해석할 descriptor/증거를 보존한다.

순서를 밟았다는 사실은 성공 근거가 아니다. 매 단계가 최신 조건과 예상 revision을 확인한다.
지원하지 않는 관측/중단/중간 인계는 제한으로 반환하며, 그 제한을 만족시키는 업무만 배정한다.

## 6. 여러 자원의 묶음 수락 — RR01

이미 구현된 `UpperBound`, `ReservedCapacity`, `ExclusiveAccess`, `SharedAccess`, `NotRequired`,
`Unknown`의 의미 구분을 유지한다. 상한은 용량 예약이 아니며, `Unknown`은 요구 없음이 아니다.
공유 장치·버스·파일 경로는 별칭을 정규 자원 신원으로 해석한 근거를 가져야 한다. 권한은 해석된
실제 대상에 대해 확인하고 나서 I/O한다. RX 밖의 임의 제어 프로그램까지 차단했다는 주장은 별도 집행 근거가 필요하다.

### 6.1 절차와 기록 경계

| 단계 | Platform 기록/판단 | 호스트·장비 측 처리 | 실패·유실 |
|---|---|---|---|
| 제안 | request, instance, 모든 요구·의존·정책 revision을 고정 | 지원 가능 범위만 보고 | 일부 지원만으로 시작 금지 |
| 예약 | 충돌하는 논리적 자원 묶음을 한 트랜잭션에서 전부 예약하거나 전부 거절 | 아직 업무 효과 없음 | 일부만 잡은 채 다른 논리 자원을 기다리지 않음 |
| 준비 | 원 예약과 만료/철회 상태를 조회 가능하게 기록 | OS 제한·접근 준비를 적용하고 원 요청의 사실을 보고 | 완전 적용, 미적용 확인, 불명을 구분 |
| 사용 확정 | instance/claim/준비 근거/의존/revision/시간을 다시 대조하고 사용 범위를 원자적으로 기록 | Host가 실제 명령 직전에 현재 조건을 다시 집행 | 유실 시 원 요청 조회; 새 효과 요청으로 대체 금지 |
| 종료·회수 | 예약 취소, 점유 해제, 격리의 서로 다른 결과 기록 | 실제 release/support/잔여 명령 근거 제공 | 효과 가능성이 있으면 TTL만으로 자원을 free로 바꾸지 않음 |

이것은 P의 DB와 OS·물리 장비를 하나의 원자 트랜잭션이라고 부르는 모델이 아니다. DB의 원자적 예약과
실제 준비·효과의 관측을 나누고 부분 실패를 기록한다. 업무 효과 없는 준비만 이 단계에서 허용한다.
시작 자체에 외부 효과가 있으면 준비용 허용 범위를 먼저 확인하는 별도 수행으로 기록한다.

준비 거절 후 해제가 확인된 논리 예약은 종료할 수 있다. 준비의 적용 또는 철회가 불명이면 이를 격리하고
원 claim으로 조회·조사한다. 새 요청/새 프로세스를 만들어 불명인 획득을 반복하지 않는다. 자원 우선순위는
정책 입력이지만 deadlock을 만들지 않는 묶음 수락과 남은 의무 보존은 공통 규칙이다.

## 7. 의존 기능의 결합과 갱신 — RR02

의존 선언은 기능/의미/호환 범위와 **사용 단계**(설치, 시작, 현재 준비, 매 수행)를 포함한다.
Platform은 결합 revision과 제공 component/instance의 관계를 소유한다. Supervisor는 instance와 OS 사실,
관측 제공자는 자신의 값·시각·품질·generation만 보고한다. 준비·업무 사용의 최종 판단을 자기 보고에 위임하지 않는다.

- 제공 기능의 상실, source generation 변경, stale 관측, 권한 철회는 관련 결합의 현재 사용 가능성을 무효화한다.
- 영향 closure는 현재 진행 작업·공유 자원·결과 소비자까지 계산한다. 관련 없는 실행은 이유 없이 일괄 중단하지 않는다.
- 매 수행에 필요한 조건은 dispatch 직전 다시 확인한다. 준비 시 PASS가 이후 무기한 허가가 되지 않는다.
- binding 교체는 후보 revision을 검토하고 새 업무에 적용할 경계를 기록한다. 기존 작업의 제공자와 결과 해석을 조용히 바꾸지 않는다.
- 관측 전용 참여는 별도 관측 권한으로 등록·결합한다. 읽기를 위해 실행 grant나 장비 제어권을 조작하지 않는다.
- 제공자 복귀는 같은 이름/PID/포트가 아니라 instance·generation·계약·현재 사실로 확인한다.
  불명인 기존 수행은 새 제공자의 성공으로 대체하지 않는다.

## 8. 운영 중 추가·교체·제거

변경 요청은 before/after 구성, 영향 closure, 원 요청 key, 기대 revision과 정책을 고정한다.
최초 기본 전환은 사용자 결정 OD04의 **다음 작업부터**다. 중간 물리 인계의 모델과 필요한 근거는 유지하되,
실제 capability가 없는 장비에 그 전환을 허용하지 않는다.

`제안 → 검토 → 새 배정 경계 설정 → 대상 준비 → 적용 의도 지속 기록 → 실제 적용 → 관측 대조 → 활성 구성 확정`

각 단계의 결과를 원 request로 조회한다. 파일이 바뀌었다거나 프로세스가 시작됐다는 이유만으로 확정하지 않는다.
일부 적용 또는 응답 유실은 실제 상태와 대조한다. 되돌리기는 이전 소프트웨어 복원과 이미 발생한 효과를 구분한다.
이전 실행·새 실행이 동시에 같은 독점 자원을 사용하는 것을 변경 과정이라는 이유로 허용하지 않는다.

퇴역은 새 업무 수용 금지와 남은 의무 종결을 구분한다. 기록과 결과를 참조하는 소비자가 있으면 해석 자료를 남긴다.
소비자의 결합 갱신 책임은 §7을 따른다. 변경 상태와 업무 수행 상태를 하나의 성공 플래그로 합치지 않는다.

## 9. 장애·복구와 프레임워크 자체 변경 — RR03

| 상실·변경 대상 | 보존할 것 | 유보/무효화할 것 | 복귀의 근거 |
|---|---|---|---|
| UI·CLI·통신 | 원 요청, P의 상태, 수행·claim | 응답을 모르는 새 중복 요청 | 같은 요청 조회와 현재 인증 |
| 기능 instance | 등록, 원 수행, 결합·자원 의무 | 해당 instance의 준비와 이후 사용 | 실제 소유/종료·잔여 효과·새 instance 대조 |
| Supervisor | P의 등록·배정, host 실행 기록 | 확인되지 않은 process 소유·자원 적용 | host boot와 실제 process identity; PID만으로 채택 금지 |
| Host | 원 operation·native journal·claim | 이전 boot의 명령 허가·관측 신선도 | 기존 재수용·origin·fresh receipt·명시적 정산 |
| Platform | 원장·원 요청·등록·변경·미결 | 이전 boot의 세션·신규 판단·grant 부활 | 원장 무결성, host 대조, 새 세대와 필요한 재자격 |
| 저장 복원 | 이전 기록의 출처·의미, 알려진 미결 | 과거 snapshot을 현재 상태로 사용하는 것 | 새 store generation, 관련 Host 최대값을 넘는 epoch, 실제 상태 대조 |
| 코어 업그레이드 | ID·요청 관계·기록 해석·의무 | 이행 중 신규 admission과 호환성 미확인 실행 | 검증된 migration, 버전/계약 대조, 현 상태 재확인 |

코어 업그레이드의 기본 경로는 `신규 admission 제한 → 진행 작업과 로컬 수행 조건 대조 → checkpoint/backup →
종료 확인 → 새 코어 기동·migration → 재대조 → serving`이다. 모든 프로세스의 무중단을 약속하지 않는다.
관리 상실 동안 지속 가능한 로컬 행동은 사전에 승인된 bounded authority와 로컬 조건 안에서만 가능하며,
그 조건을 확인할 수 없으면 해당 계약의 중단·불명·보호 경로로 간다.

미해결 과거 결과를 반드시 성공으로 바꿔야 새 업무가 가능한 구조를 만들지 않는다. 결과는 미해결로 남아도
현재 자원·잔여 명령·소유권을 별도로 확인한 처분과 새 허가를 통해 진행할 수 있어야 한다.
증거가 없을 때는 보류 이유와 필요한 관측/사람 조치/지원 제외 경로를 명시한다.

다운그레이드·전체 저장 rollback은 검증된 이행 경로가 있을 때만 지원한다. 오래된 snapshot의 epoch에 1만
더한 값이 Host의 현재 최대값보다 크다는 가정을 하지 않는다. 기존 OI11/OI17 공백을 해결해야 이 행을 구현 완료로 셀 수 있다.

## 10. 분산·원격 관리와 지원 범위

운영 영역의 공식 갱신자는 해당 범위의 충돌을 직렬화한다. 다른 영역이나 remote client는 출처·역할·대상·시간
조건이 확인된 요청으로 참여한다. 관측 freshness에는 clock domain과 불확실성 범위를 포함한다. 연결 성공을
상태 대조나 권한 위임의 증거로 사용하지 않는다. 단절 중 다른 영역이 같은 충돌 자원을 임의로 새 소유자에게 줄 수 없다.

원격 유지보수는 조회, 증거 수집, 변경 제안/승인, 적용, 결과 확인을 각각 인증·권한·감사 기록과 연결한다.
원격 접속권이 물리 명령 권한이 되지 않는다. 현장에서만 가능한 확인·보호·복구를 원격 소프트웨어가 수행했다고 표시하지 않는다.
다중 호스트/영역의 실제 위임·시계·단절 시험은 후속 검증 게이트로 남긴다. 단일 호스트 시험을 그 증거로 승격하지 않는다.

## 11. 구현과 이행

| 모델 책임 | 우선 연결할 기존 경로 | 필요한 구현/검증 |
|---|---|---|
| 공통 등록·선언 | S Registry, P package intake와 application writer | P authoritative registration, S 실행 보고, 기존 ID/이력 수입 |
| 묶음 수락 | S execution requirements, P resource/permit | 원 요청으로 준비·commit·불명·해제를 연결하는 계약과 실제 OS 집행 |
| 의존 결합 | S readiness/dependency/decision, P observation/condition | 관측 전용 등록, 결합 revision과 영향 전파, 매 사용 재검사 |
| 작업·변경·복구 | P Engine/Host gate/process change/readmission/settlement | OI08 재개, OI11/OI17 복원, restarted-Host 정산, 같은 설치의 복귀 |
| 확장·저작 | device/process packages, Python client, native adapter ports | manifest/어댑터 revision, 열린 registry, 외부 프로세스·컴파일 확장, conformance |
| 지속 운영 | platformd/solutionsd, operator UI, journals | public read/command 경로, 이벤트·보존·백업·업그레이드·원격 관리 |

기존 코어를 유지·보강한다. 새로운 API가 기존 판정을 복제하지 않고 같은 application 경로를 사용하도록 한다.
서명 검증·UNKNOWN·결과·claim 판정은 패키지에 넘기지 않는다. shared 형식은 platform 원본에서 SDK를 재생성한다.
규범·persisted schema·wire가 바뀌는 구현은 별도 revision/impact와 양방향 호환·거절 시험을 포함한다.

## 12. 모델과 전체 Goal의 검증

[기존 AC01–AC18](44_resident_framework_concept.md#13-대표-시나리오와-수락-관찰)은 유지한다. 추가로 다음 반례를 확인한다.

| ID | 반례 | 관찰해야 할 결과 |
|---|---|---|
| MC01 | CPU 적용 후 장치 준비 거절/응답 유실 | 업무 시작 없음; 미적용 확인과 불명 분리; 남은 claim/조사 책임 보존 |
| MC02 | 두 작업이 카메라·공간을 반대 순서로 요구 | 논리 묶음의 일부만 확보한 대기가 없고, 물리 불명을 TTL로 해제하지 않음 |
| MC03 | 등록 자료 이행 중 P 또는 S가 종료 | stable ID/이력 보존, 동시에 둘이 등록 상태를 쓰지 않음 |
| MC04 | 소비 중인 관측 제공자가 같은 이름으로 재시작 | 새 instance/generation 확인 전 결과 소비·업무 사용 제한 |
| MC05 | A 실행 중 B 추가 후 다음 작업부터 교체 | A의 기록/결과 의미 유지, 새 binding으로 새 작업 실행, 독점 자원 중복 사용 없음 |
| MC06 | 코어 교체 중 늦은 ACK 또는 과거 permit 도착 | 새 세대의 허가가 되지 않으며 원 요청 조회/정산 가능 |
| MC07 | 오래된 backup의 epoch가 살아 있는 Host보다 낮음 | Host 최대값과 대조 전 serving/새 허가 금지, 충분히 큰 새 epoch와 재대조 |
| MC08 | 업무 결과 미해결이나 현재 자원 복구가 입증됨 | 과거 결과를 고치지 않고 별도 처분·인계·새 업무 허용 |
| MC09 | 관측 전용 package가 제어 호출 또는 임의 grant 요청 | 명시적으로 거절; 관측 등록 자체에는 제어 권한이 필요하지 않음 |
| MC10 | 원격 관리 연결 상실 후 같은 변경 요청 재전달 | 원 변경의 단계/효과 조회; 새로운 교체나 물리 명령 자동 반복 없음 |

모든 사례에 양성 경로도 필요하다. 거절만 늘려서 검사에 통과한 구현은 완료가 아니다.
불변식 30개의 책임별 실제 시험, 10k seed, 결함 주입 행렬, 24시간 soak, 이기종 두 계열,
두 번째 적용 환경의 코어 수정 0줄과 작성/진단/복구 비용 측정이라는 기존 계획의 게이트를 유지한다.
문서의 상태·ID가 모두 존재하는 검사는 의미의 충분성이나 실행 적합성을 증명하지 않는다.
